# 深度重构（deep-refactor）

手动进入：用户输入 `/deep-refactor`。本技能不依赖本机是否另装了 `grill-me`。

调用期间，`doc-sync` 的守成立场暂停：不得只因 `doc/design/` 已写死而拒绝重开。用户通过总结、文档落地之后，新正文才是契约，此后仍交 `doc-sync` 守住。

本技能讨论。用户接受一条决定后，当轮写入 `doc/重构.md`。每个切片两块：「已定决策」记已经接受的设计；「子切片功能」是最多 3 层的树，按优先级和依赖排序。切片表只留第 1 层，一行一句范围。设计文档等到用户通过总结之后再改。不写生产代码，不写、不改测试，不改决策日志。代码留到用户另说「开始实施」，并只实现状态为「当前」的那个叶子。「开始实施」不改 `doc/重构.md`。

`doc/重构.md` 只记进行中的重构，不是设计契约。设计文档不要指向它。

## 立场

允许重开协议、模块边界、线程 / 执行模型，以及文档里写死的行为。仓库里能查到的事实自己读代码和设计文档，不要拿去问用户。需要用户拍板的才发问。

## 进入时

先读 `doc/重构.md`（没有这个文件就跳过）。某一节里第 1 层每一片都已落地时，删掉这一节。删完没有任何进行中的重构时，保留文件，内容只留：

```markdown
# 重构

当前无进行中的重构。
```

不删除该文件。这一步不需要用户再说「通过」。

当前叶子的代码还没落地，就不要把下一个叶子提升为当前。父节点在全部子节点已落地之前，不算已落地。

## 讨论

### 范围

用户没有说明要动哪一块时，第一轮只问两件事：目标和范围。不要扫整个引擎，也不要开始谈方向或拆切片。

### 方向

这次重构还没有约定方向时，范围清楚后先问四项：收益、劣势、方向、影响。用户接受这个方向之后才拆切片。用户不接受，就停住，不拆切片，不改文件。

`doc/重构.md` 里已有这次重构的目的、且用户没有要求重开方向时，沿用那四项。切片讨论中，只有某条决定改变了其中一项，才改写它。

### 先拆再细问

方向已经接受之后，把工作拆成树，定优先级和依赖。

- 第 1 层写进切片表。第 2、3 层写在该切片的「子切片功能」里。第 3 层不再往下拆。
- 树表示谁包含谁。先后由优先级和依赖决定。依赖可以指向兄弟，不限于父节点。每个节点写明依赖。
- 缺了就不能单独验收的功能留在同一个叶子里，不往下拆。
- 一次只有一个叶子是「当前」。「开始实施」只做这个叶子。有子节点时，第 1 层表的状态由子节点汇总：有一个子节点是当前，父就是当前；全部已落地，父才是已落地。没有子节点时，表上的状态就是这个叶子的状态。互不依赖的叶子也按优先级一次只取一个。
- 细问只覆盖当前叶子。待开发的上层切片不展开子树；展开留到它成为当前片、准备实施之前。讨论里已经落定、属于后片的决定，写入后片自己的「已定决策」，不为此加细。

### 一轮一前沿

把决定画成问题树。**前沿**是前提已经定下来、现在就能问的问题。一轮把整条前沿编号列出，每题附推荐答案，然后停下等用户答。依赖本轮尚未听到的答案的问题留到下一轮。

问法写成「同意即接受推荐答案」：

```text
❓ Q1 - <标题>：<问题>

➡️ <推荐答案>
```

用户的回答会改写问题树。前沿排空之前不总结、不改设计文档。低优先级切片不要为了“问全”而加细。

### 落定即写入

用户接受某一条（方向四项、切片划分，或某一问的推荐答案）后，同一轮写入 `doc/重构.md`。不等前沿排空，也不等整次「通过」。还没接受的不写。没有这个文件就创建。一次重构一节，沿用已有的那一节，不另开重复的节。

- **方向被接受**：写入或改写该节的目的（收益、劣势、方向、影响）。之后只有某条决定改变了其中一项，才改写它。
- **切片划分被接受**：写入或改写第 1 层切片表，以及当前片的「子切片功能」。表只留切片、优先级、依赖、状态、一句话范围。协议、时序、删除清单不进表。状态只有「当前」「待开发」「已落地」。表里只有一行是「当前」。待开发片不展开子树。
- **某一问被接受**：写入做出该决定的那一层的「已定决策」。子节点不复制父节点已经写过的条目。用短条目，按落定顺序写。当前叶子若已有设计正文，该层首行指向该章节，并保留同样的要点。推翻一条已写入的决定时，改它所在的那一层，不另留废案。

每个切片（含第 2、3 层节点）都是这两块：

```markdown
### <切片名>（<状态>）

#### 已定决策

- <短条目>

#### 子切片功能

1. <名> — 优先级 1，依赖：无，状态：当前
2. <名> — 优先级 2，依赖：1，状态：待开发
   1. <再下一层，到第 3 层为止>
```

本片不再向下拆时，「子切片功能」写明它是一个叶子。尚未展开时写：成为当前片之前不展开。

`doc/重构.md` 不是设计契约。设计文档仍等通过后再改。叶子通过时补该叶子的验收要点；没有推翻契约时，不重写已经写过的正文。

## 总结

前沿排空后，在会话里给出简短总结，然后停住。这一轮不改设计文档。总结里列出的决定若还没进 `doc/重构.md`，先补进对应层的「已定决策」再停。

总结只含这几块：

1. 目标与范围
2. 收益、劣势、方向、影响（最新一版）
3. 切片树：当前叶子写全；其余为待开发（目标、优先级、依赖）。待开发的上层切片不展开子树
4. 当前叶子的新方案（一段话）
5. 当前叶子推翻的文档与章节
6. 当前叶子的验收要点改法
7. 供用户摘进决策日志的短清单

## 通过

只有用户明确同意才算通过：回复「通过」「可以」或「确认」，且没有新的反对、没有改某一条决定。一句通过授权改相关设计文档，并核对 `doc/重构.md` 的目的、切片表、当前叶子的「已定决策」和「子切片功能」与总结一致。每个叶子通过时，设计文档补上该叶子自己的验收要点。契约正文已经覆盖该叶子、且没有被推翻时，不重写正文，只补验收行。

用户要改某一条，回到讨论，前沿重新打开，不改设计文档。新答案被接受后，按「落定即写入」改它所在那一层的「已定决策」。

## 落地

通过的那一轮，若当前叶子的契约尚未写入设计文档，立刻写入。落定的决定已在 `doc/重构.md`；这一轮只核对，不把决定留到这时才第一次写入。代码已经进入代码库的旧当前叶子，在这一轮标成「已落地」，父节点按子节点汇总。

1. **进度**：核对 `doc/重构.md` 该节。目的四项是最新一版。切片表一句话范围。当前叶子的「已定决策」和「子切片功能」与总结一致。

2. **当前叶子的正文**：改相关设计文档，使它描述新方案。被推翻的旧条款写入该文档的「问题自查」（列：`#` / 问题 / 关联章节 / 状态），状态写「已解决」。不留「待讨论」占位，也不要顺手关掉与这次无关的待讨论行。没有这一节就按上述列新建。设计文档里不写切片树，也不要指向 `doc/重构.md`。

3. **验收要点**：当前叶子必须有自己的验收行，父切片的契约不能代替。只改该叶子涉及的行。沿用该文档既有列。新码遵守 `doc/测试验收码.md` 和该文档既有前缀；已分配的码不改名、不复用、不重排。不写 Catch2。没有这些验收行、或没有对应该叶子的测试用例时，不开始实施。测试在实施前的验收轮写，不在讨论轮写。

4. **其他设计文档**：只更新当前叶子推翻的条款。不在每份文档里复制切片表。

5. **引用**：设计文档的正文、标题或编号变了之后，同步 `doc/` 里指向它们的链接和「详见 §」。决策日志不在此列。

6. **不改**：生产代码、测试、`**/决策日志/`、文件名含「决策日志」的文件。

落地后在会话里重复那份决策日志摘记，并写明：决策日志由用户亲手维护；「开始实施」只做状态为「当前」的叶子，且该叶子已有验收要点和对应测试。这一步不改 `doc/重构.md`。

## 下一片

当前叶子的实现已经进入代码库之后，用户再次 `/deep-refactor`，才把下一个叶子细问并更新文档，然后才可以开始实施那一个叶子。下一个叶子若属于尚未展开的上层切片，先展开它的子树，再细问当前叶子。待开发叶子在变成当前之前，不是实现范围。
