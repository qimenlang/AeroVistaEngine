**把“读代码”换成“写约束 + 验证据”。**把人的精力上移到规格、验收契约和质量闸门上；AI 负责实现，机器负责证明“没撒谎”。

---

**行为可验证 + 测试质量可度量**，比人眼逐行读 AI 产出更划算。


| 条件                                   | 为什么重要                           |
| -------------------------------------- | ------------------------------------ |
| 需求能写成可执行规格（Gherkin / ATDD） | 否则 AI 仍在猜你想要什么             |
| 测试不是 AI 自己“随便补”的             | 否则会出现“测自己写的假想行为”       |
| 有变异测试等“测测试”的手段             | 覆盖率高≠测试有效                    |
| 领域边界清晰、副作用可观察             | 数学/场景图/资源管线最合适；像素外观需黄金图或阈值 |


**不适用或要打折的场景：** 强依赖架构审美、渲染观感主观判断、性能热点调优、遗留系统里“没规格只有代码”的改造。那些地方仍需要人读关键路径，或由 QA 做视觉抽检。

### 1. 单元测试（Unit Tests）

测最小可验证单元（函数/类/模块），输入→输出/状态变化要确定。  
对 AI：约束“局部逻辑别乱写”；但只有单测不够——AI 很会写“看起来对、断言很弱”的单测。

图形引擎典型对象：矩阵分解、AABB 合并、视锥裁剪判定、LOD 切换阈值、资源句柄引用计数、场景图节点挂载/卸载。

### 2. 验收测试（BDD / Gherkin 测试）

用自然语言场景描述**可观察行为**，再落到可执行测试（Cucumber、Catch2 BDD、自定义 runner 等）。  
Uncle Bob 路线里，Gherkin 往往是 AI 实现时真正“看见”的规格；人审规格，而不是审每一行实现。

#### 简略写法与格式

核心结构只有四层：

```text
Feature: <能力/子系统名>
  <可选：一两句业务目的>

  Scenario: <一个可判定的结果>
    Given <前置状态 / 已加载资源 / 相机与场景>
    When  <触发动作：一帧渲染、加载模型、改视口…>
    Then  <可观测断言：文件写出、尺寸、误差阈值、状态标志…>
    And   <补充断言，可选>
```

书写要点（图形引擎）：

| 要点 | 说明 |
| ---- | ---- |
| 一 Scenario 一事 | 不要在一个场景里同时验收“加载成功 + 阴影正确 + 60fps” |
| Given 写状态，不写实现 | 写“已加载 teapot.vsgt”，不写“调用 `Engine::init` 第 3 步” |
| Then 必须可机器判定 | 优先：尺寸、像素差%、PSNR、节点数、错误码；避免“画面好看” |
| 数值带阈值 | GPU/驱动差异常见，写 `< 0.1%`、`PSNR > 40dB`，不要要求逐像素 bit-exact |
| 标签可辅助分层 | 如 `@render @smoke`，便于 CI 只跑冒烟 |

图形引擎示例：

```gherkin
Feature: 离屏渲染与黄金图回归
  验证固定场景在无窗口模式下输出稳定画面。

  Scenario: teapot 默认相机渲染与黄金图一致
    Given 引擎以 1920x1080 离屏模式启动
    And 已加载模型 "models/teapot.vsgt"
    And 黄金参考图为 "renderingTests/teapot.png"
    When 执行一帧渲染并截屏到实际图
    Then 实际图与黄金图尺寸一致
    And 像素差异比例 < 0.1%
    And 最大绝对误差 < 32
    And PSNR > 40 dB

  Scenario: 模型路径不存在时初始化失败
    Given 引擎以离屏模式启动
    When 加载不存在的模型 "models/missing.vsgt"
    Then 初始化返回失败
    And 不产生截屏文件
```

```gherkin
Feature: 视锥裁剪
  Scenario: 完全在视锥外的物体被剔除
    Given 场景中有一个 AABB 完全位于相机视锥外的网格
    When 执行可见性剔除
    Then 该网格不进入绘制列表
```

人维护 Feature/Scenario；AI 只负责让对应自动化步骤变绿（本仓库已有 `RenderingTests` + `ImageCompare` 可作为 `Then` 的落地）。

#### BDD 本质与用法（精炼）

Catch2 的 `SCENARIO` / `GIVEN` / `WHEN` / `THEN` **不会替你生成断言**，只是把普通测试组织成可读规格；调用 `Engine`、写 `REQUIRE` 的步骤代码仍要人（或 AI）编写。价值不在语法糖，而在**规格驱动**：人锁定行为契约，实现（含 AI）去把红测变绿。

**开发节奏（ATDD / TDD）：**

```text
人写/审 Scenario（可执行） → 跑测为红 → 写最少实现让它绿 → 重构（规格不变） → 下一 Scenario
```

BDD **能测代码**：跑的是真实生产代码，通过公共 API / 协议 / 截图等可观察结果约束行为。它测的是“对外该怎样表现”，不直接断言私有实现细节。

**不要用 BDD 取代全部单元测试。** 二者互补，不是二选一：

| | BDD / 验收 | 单元测试 |
|--|-----------|---------|
| 问什么 | 系统该不该这样表现？ | 这段实现算得对不对？ |
| 粒度 | 跨模块、用户/宿主可见故事 | 函数/类/算法 |
| 数量 | 少量、稳定、钉契约 | 大量、快速、保细节 |

- 每个小函数都套 Given/When/Then → 叙事变噪音，维护成本高。  
- 业界许多项目只有单测、少见 BDD，并不等于测试不成熟；完整 Gherkin 工具链有协作成本。  
- **本工程建议**：对外行为用 BDD（如加载模型并成功跑一帧、CIGI 收发）；数学/裁剪/工具逻辑继续普通 `TEST_CASE`。比例示意：**少量 BDD 钉契约 + 大量单测保细节**。

### 3. QA（质量保证流程）

自动化证明“规格内行为成立”；**QA 负责规格外、主观与组合风险**。  
含义是：**自动化闸门 + 有节奏的人工验收**，不是“有测试就完事”。

#### 具体作用

| 作用 | 说明 |
| ---- | ---- |
| 补自动化盲区 | 闪烁、接缝、错误的曝光感、UI 遮挡等难写成稳定断言的问题 |
| 发布门禁 | 版本是否可合入/可交付的最终签字，而不只是 CI 绿灯 |
| 探索性测试 | 故意偏离脚本：极端分辨率、缺资源、连续热加载、多显示器 |
| 回归清单 | 每次改渲染管线后必看的固定镜头与场景包 |
| 反馈规格缺口 | 发现“规格没写但用户会碰到”的路径，回写成新的 Gherkin/单测 |

#### 简单示例（图形引擎）

**发布前视觉抽检清单（节选）：**

1. 启动默认场景：窗口模式与离屏模式各跑一遍，无黑屏、无持续粉紫（未绑定纹理常见症状）。  
2. 切换 1280×720 / 1920×1080 / 超宽比，确认视口与深度缓冲无拉伸错乱。  
3. 连续 10 次加载/卸载同一模型，观察显存与主机内存是否回落。  
4. 故意指向缺失纹理路径：应有明确失败/占位，而不是静默花屏。  
5. 对比上一版本同镜头截图：若自动化未覆盖的特效（如后期），由人判定是否可接受。

QA 不替代黄金图测试；它处理**阈值测不住、组合测不完**的部分，并把新发现沉淀回自动化。

### 4. 覆盖率（Coverage）

代码被测试执行到的比例（行 / 分支 / 条件等）。  
用途：找“完全没被碰到的代码”。  
陷阱：AI 很容易刷出高覆盖、弱断言；所以需要变异测试等配套。

#### 原理（简略）

1. **插桩**：编译或运行时在基本块/分支处插入计数探针（或用调试信息做基于采样的近似）。  
2. **执行**：跑单元测试、渲染测试等，探针记录“走到了哪些行/分支”。  
3. **汇总**：`覆盖率 = 被执行到的条目 / 可执行条目`。  
4. **门禁**：CI 比较当前覆盖与阈值（或与基线的差），未达标则失败。

常见口径：

| 口径 | 含义 | 图形引擎注意 |
| ---- | ---- | ------------ |
| 行覆盖 | 某行是否执行过 | 最易获得，也最易被刷 |
| 分支覆盖 | `if/else`、循环出口是否都走到 | 对裁剪、LOD、错误路径更有意义 |
| 条件/MC/DC | 复合条件的各关键组合 | 航空/安全相关逻辑才常强制；引擎数学核可选 |

覆盖率只回答“测没测到”，不回答“断言对不对”。

#### 实现方式（C++ / 本类工程）

本仓库为 CMake + Catch2，常见做法：

1. **Debug/覆盖构建**打开插桩，例如 GCC/Clang：`-fprofile-arcs -ftest-coverage`（或 `--coverage`）；MSVC 可用 OpenCppCoverage / 类似工具。  
2. **跑测试**：`ctest` 或直接跑 `vsgEngineTests`、`RenderingTests`。  
3. **生成报告**：`llvm-cov`、`gcovr`、`lcov` 等汇总为 HTML/JSON。  
4. **设门槛**：例如核心数学/场景图目录行覆盖 ≥ 80%，分支 ≥ 70%；第三方与生成代码排除。  
5. **分层看待**：着色器、GPU 驱动回调、平台窗口代码往往难覆盖——单独划“豁免目录”，避免 AI 为刷覆盖写空调用。

原则：覆盖率是**入场券**；变异测试/黄金图才更接近“测试有没有牙齿”。

### 5. 代码质量指标（Quality Metrics）

例如：圈复杂度、模块大小、依赖方向、重复度、静态分析告警、架构规则。  
用途：推断“可维护性是否失控”，不直接证明功能正确。  
Uncle Bob 说“从指标推断质量”——合理，但**推不出正确性**。

#### 代码质量标准如何生成？

标准不是一次拍脑袋写死，建议按下面步骤**生成并迭代**：

1. **先量基线**  
   对当前仓库跑静态分析与度量（clang-tidy、cppcheck、Include-What-You-Use、依赖图、复杂度统计），记录现状分布（P50/P90），而不是理想值。

2. **按风险分层定标**  
   - 热路径 / 数学核 / 资源生命周期：更严（复杂度、禁止裸 `new` 泄漏模式、明确所有权）。  
   - 示例/工具/第三方封装：更松。  
   - 渲染后端适配层：允许一定平台分支，但限制循环依赖。

3. **写成可执行规则，而非散文**  
   例如：  
   - 单函数圈复杂度 ≤ 15（超限须拆分或标注豁免）。  
   - `engine/` 不得依赖 `examples/`。  
   - 场景节点与 Vulkan 句柄的销毁顺序有检查清单/静态规则。  
   - clang-tidy 指定检查集在 CI 零新增（允许 baseline 消债）。

4. **与架构决策对齐**  
   质量标准应反映引擎分层（资源 → 场景图 → 渲染 → 应用），AI 提交若破坏依赖方向则直接失败。

5. **用 PR 反馈收紧**  
   每次事故（泄漏、错误依赖、万行文件）补一条规则；每季度按误报率放宽或替换规则。  
   **生成公式**：`标准 = 基线度量 + 架构约束 + 事故教训 − 误报豁免`。

图形引擎可优先落地的指标示例：

| 指标 | 示例门槛 | 约束 AI 的作用 |
| ---- | -------- | -------------- |
| 圈复杂度 | 核心模块函数 ≤ 15 | 阻止“一个 Update 里写完所有管线” |
| 文件/类体量 | 单 .cpp 建议 < 800 行 | 逼迫拆分 Renderer / Cull / Resource |
| 依赖方向 | 禁止上层被下层反向 include | 防止示例代码污染引擎核 |
| 静态告警 | tidy 新增 = 0 | 挡住未初始化、错误 move、悬空风险 |
| 重复度 | 复制粘贴阈值告警 | 减少 AI 复制三份几乎相同的加载逻辑 |

### 6. 变异测试（Mutation Testing）

故意把生产代码改坏（`>` 改成 `>=`、删掉条件等），再跑测试：  

- 测试失败 → “杀死变异体”，说明测试有牙齿  
- 测试仍通过 → 测试薄弱

工具如 mutagen（C/C++ 生态较分散）、或对纯逻辑库使用可插桩方案；也可先对**非 GPU 的数学/裁剪/资源状态机**子集做变异。  
这是对 AI 时代特别关键的一层：**防止 AI 写出“高覆盖空壳测试”**。

图形引擎建议范围：AABB/视锥、变换链、LOD 选择、资源状态机；像素对比与 GPU 时序暂不作为变异主战场（成本高、噪声大）。

## 测试分层与 Catch2 用法（本工程约定）

分层看**测什么、问什么**，不看用了哪个框架。Catch2 的 `TEST_CASE` / `SCENARIO` 都能写任一层级；形式 ≠ 测试类型。

### 四层定义（精炼）

```text
单元     → 零件算得对不对
集成     → 模块拼起来接得对不对
系统     → 整机在目标环境里跑得怎样
验收     → 该不该按约定收货（常以系统级手段执行）
```

| 层级 | 关注点 | 范围与依赖 | 谁定标准 | 本工程例子 |
| ---- | ------ | ---------- | -------- | ---------- |
| **单元** | 局部逻辑正确 | 单函数/类；协作方可 mock | 开发 | 将来的 AABB/矩阵；`compareImages` 阈值本身 |
| **集成** | 接口、协议、数据流 | **多个真实模块**协作；边界外可真可假 | 开发/架构 | `SynchronSystem` + 本地 UDP + MiniHost 收发 |
| **系统** | 完整系统行为与环境 | 倾向真 GPU / 真文件 / 准真实环境 | 测试/开发 | 离屏 `Engine` 加载→渲染→截屏 |
| **验收** | 需求/契约是否达成 | 按验收标准选场景；执行上常像系统测 | **产品/规格** | 黄金图 BDD、加载失败 BDD |

**易混点：**

- 「mock 外部、测本系统 I/O」→ 常叫**组件测试 / 带边界 mock 的集成**；集成的核心是「连接是否正确」，不是「必须 mock」。  
- 「真实外部砸整系统」→ 更偏**系统 / E2E**。  
- **系统 ≠ 验收**：执行形态可以相同（都跑真 `Engine`），差别在是否代表**收货标准**。黄金图用例执行上像系统测试，角色上是验收/视觉回归。  
- 用 Catch2 写、放在 `*Tests.cpp` 里 → **不自动等于单元测试**。原先「茶壶黄金图」`TEST_CASE` 一直是验收/回归，改成 `SCENARIO` 只换叙事，断言相同时不必再留一份重复用例。

**区分三问：** ① 失败时产品语言能否听懂？能 → 偏验收；② 是否一个完整对外故事？是 → 偏验收/系统；③ 是否必须串起多子系统/真环境？是 → 偏集成/系统，否则偏单元。

### Catch2：`TEST_CASE` 还是 `SCENARIO`？

| 形式 | 含义 | 何时用 |
| ---- | ---- | ------ |
| `TEST_CASE` | 普通用例组织 | **技术验证默认项**：单元、多数集成、系统冒烟 |
| `SCENARIO` + `GIVEN`/`WHEN`/`THEN` | 同一套断言的可读规格外壳 | **交付契约 / ATDD**：给人审、给 AI 当红测目标 |

口诀：**技术拼装 → `TEST_CASE`；交付故事 → `SCENARIO`。** 集成测试不必硬套 BDD；验收也不必上完整 Cucumber——Catch2 BDD 足够。

- Catch2 **可以**写单元 / 集成 / 系统 / 验收；限制在环境（GPU、多进程、超时），不在框架。  
- 集成例（SynchronSystem ↔ MiniHost）：默认 `TEST_CASE` + 标签 `[integration][cigi]`；关键收货路径再抽少量 `SCENARIO`。需编排：拉起 MiniHost → 等端口 → 跑同步 → 断言 → 清理。  
- 系统/验收例：现有 `RenderingTests`（加载、失败路径、黄金图）即 Catch2 系统级执行 + 验收叙事。  
- 标签建议：`[bdd]` 验收故事、`[integration]` 集成、`[render][golden]` 视觉回归，便于 CI 分层跑。

### 本工程怎么配（建议）

```text
大量、快速     → 单元 TEST_CASE（数学、工具、状态机）
中量、对接     → 集成 TEST_CASE（CIGI/MiniHost 等），偶发 SCENARIO
少量、钉契约   → 验收 SCENARIO（Engine 对外行为、黄金图）
发布前补充     → QA 视觉/探索（自动化盖不住的）
```

- **不要**把全部单测改成 BDD；**不要**为同一契约同时保留等价的 `TEST_CASE` 与 `SCENARIO`。  
- AI+TDD：人写/审验收与关键集成的红测 → AI 实现变绿 → 单测补细节；AI 不得擅自改 Then 含义。

### 本工程常用手法：门控与 queue 注入

写同步 / Host→IG 一类 BDD 时经常用到；二者是**测试与实现里的说法**，不是业务专有名词。

#### 门控（gating）

字面：**门 + 控制**——先过一道开关/条件，满足才放行后面的动作。

例：`SynchronSystem::update` 前「已连接 Host 才允许用 Host 眼点改写相机；未连接则不改」。

测门控 = 分别断言开关两侧行为：

| 门 | 状态 | 期望 |
| -- | ---- | ---- |
| 关 | 未连接 | 本地位姿不被覆盖 |
| 开 | 已连接 | Host 位姿（再叠标定）生效 |

注意：这里的「门控」≠ 产品里的 `frameGate`（Barrier 等齐发帧），也不是网络防火墙。

#### queue 注入（queue injection）

**绕过真实网络/报文**，把「本帧该收到的数据」直接塞进模块内部队列，再调用应用逻辑（如 `update`），断言可观察结果。

| | 端到端 | queue 注入 |
| -- | ------ | ---------- |
| 路径 | Host 打包 → UDP → 收包解析 → 入队 → update | 测试直接 `queueHostEyePose(...)`（或同类 API）→ update |
| 测什么 | 协议 + 传输 + 应用整条链 | **只测应用逻辑**（门控、offset、无新包策略等） |
| 优点 | 真 | 快、稳、不依赖端口/时序 |
| 缺点 | 慢、脆 | **测不到**打包/收包/乱序 |

「注入」= 测试像打针一样推进假数据，假装「已经收到」。本工程可用 `SynchronSystem::queueHostEyePose` 一类测试入口。  
分层建议：**应用契约先用 queue 注入钉绿**；协议与乱序另开集成/端到端场景，勿混在同一 Scenario 里既要稳又要真。

## 还可以加哪些“约束 AI”的测试？（图形引擎）

只保留对本领域性价比高的手段：

1. **黄金图 / 快照测试**（Snapshot / Golden）  
   **作用**：固定相机与场景，截屏与参考图比差异%/PSNR；改动须显式更新黄金图。  
   **用处**：渲染回归的第一道自动化闸门（本仓库 `RenderingTests` + `ImageCompare` 即此类）。对 AI 改管线、改默认状态极有效。

2. **属性测试**（Property-based）  
   **作用**：陈述不变量，随机生成输入批量验证。  
   **用处**：`quat` 归一化后模长≈1；矩阵逆·原≈单位阵；AABB 合并单调扩大；绕父节点变换后世界坐标满足结合律。专治 AI 漏边界的数学代码。

3. **模糊测试**（Fuzzing）  
   **作用**：随机/变异字节砸加载器与解析器，找崩溃与死循环。  
   **用处**：`.vsgt`/模型/纹理/地形块等资源入口；防 AI“只测幸福路径”导致的畸形文件崩溃。

4. **差分测试**（Differential）  
   **作用**：同一输入下比较两实现输出。  
   **用处**：CPU 参考裁剪 vs GPU/新裁剪；旧数学库 vs 新实现；重构前后世界矩阵。适合“换实现但不改行为”。

5. **性能与资源预算测试**  
   **作用**：帧时间、内存/显存峰值、抽检场景的 draw call 上限。  
   **用处**：防 AI 写出功能正确但每帧全量重建 Buffer、泄漏 Staging、复杂度炸掉的实现。

6. **表征测试**（Characterization）  
   **作用**：先把遗留行为（输出矩阵、节点数、截图像素摘要）钉成测试，再允许 AI 重构。  
   **用处**：读不懂的老渲染路径“先锁行为再清理”。

7. **架构 / 静态门禁**  
   **作用**：依赖方向、禁 API、clang-tidy、句柄生命周期检查。  
   **用处**：不替代功能正确性，但能挡住 AI 常见的分层破坏与低级缺陷。

## 实践上怎么落地（比口号更重要）

```text
人写/审规格 (Gherkin/验收)
    → AI 实现
    → 单测 + 验收/黄金图必须绿
    → 覆盖率门槛
    → 质量指标门槛
    → 变异测试（优先数学/状态机）
    → QA/视觉与探索性抽检
```

关键纪律：

- **规格与验收测试尽量由人掌控**；让 AI 从空实现开始把测试跑绿，而不是先写完再补测。  
- **不要让同一代理既写生产代码又“自由发明”验收标准**（或至少分角色、分审查）。  
- **覆盖率是必要条件，变异分数与黄金图阈值更接近充分条件。**  
- **人仍要读：架构边界、资源生命周期、性能热点、规格本身；观感类问题交给 QA 清单。**

---

## 简短结论

- **可行**：对场景图逻辑、数学核、资源管线、可阈值化的渲染回归尤其合适；本质是 ATDD/TDD + 度量闸门在 agentic 开发上的加强版。  
- **不是银弹**：人从“读实现”转向“写对规格、审测试有效性、守架构与风险面”；规格错或测试弱，AI 会高效地错下去。  
- **图形引擎上对 AI 最有增量价值的组合**：Gherkin/验收契约 + 单元测试 + 黄金图回归 + 覆盖率/质量门禁 +（数学核）变异/属性测试 + QA 视觉抽检。
