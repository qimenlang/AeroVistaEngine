# 状态同步设计（命令面：Host → IG 指令 + ACK）

> **⚠️ 本方案为「完整版」，暂不实现**——含 QUERY 悬挂查询、cancelCommand、双线程执行模型、多 peer 并发分发等完整机制，作为设计演进参考。
>
> **当前要实现的版本**见 [状态同步设计初版.md](./状态同步设计初版.md)（最小可用第一版）。

面向本项目 **1 Host + 多 IG（约 10 通道）** 的完整命令面设计：Host 通过 **TCP 命令面**向各 IG 下发指令（加载/切库/复位等），IG 执行后沿同一条 TCP 回执 ACK/NACK。

**完整方案一句话**：命令走 **TCP 命令面**，载荷用 **CIGI `IGMsg`（V4）**（`MsgID` 指令码 + `Msg` 变长载荷）；IG 收到命令**立即回 RECEIVED**（送达确认，短超时重发），**执行完再回 RESULT**（ACK/NACK，结果确认，不设死超时）——两段回执绕开「加载耗时不定」的超时难题；RESULT 悬挂时 Host 发 **QUERY** 查询（区分「完成/执行中/未知」，弥补 RESULT 丢失）；命令带**序号**保证幂等。

## 1. 范围与目标


| 纳入初步                                                    | 暂不纳入                         |
| ------------------------------------------------------- | ---------------------------- |
| Host 组装 `IGMsg`（指令码 + 载荷）→ TCP 下发                       | 多通道「全部 IG 齐集 ACK 后才开帧」（见 §9） |
| IG 收命令 → 立即回 **RECEIVED** → 执行 → 回 **RESULT**（ACK/NACK） | 命令队列 / 优先级调度                 |
| Host 等 RECEIVED 短超时重发（应用层）；等 RESULT 不设死超时               | 命令历史 / 回放                    |
| 命令序号 → IG 幂等去重                                          | 与 UDP 同步面数据共享状态              |
| TCP 命令读写循环（Host / IG 两侧）                                | 独立 Host 进程的命令中心              |


**目标**：跑通「Host 发指令 → IG 确认收到 → IG 执行 → 回结果 → Host 判定」的闭环。指令「执行与否」必须有答案（ACK/NACK），「送达」用短超时重发兜底。

**关键认知**：

- ACK/NACK 是**应用层协议**，不是 TCP 机制。TCP 只保证「字节送达」，不保证「命令执行成功」；
- **两段回执**：`RECEIVED`（收到确认，瞬时，短超时重发）与 `RESULT`（执行结果，耗时不定，不设死超时）分离——解决「不同指令 / 同指令不同规模耗时差异大，统一超时阈值必然两难」的问题；
- TCP 重发管「网络」，应用层重发管「对端是否真的处理并给结果」，二者不重叠。

## 2. 报文与协议



### 2.1 载荷：CIGI `IGMsg`（V4）

沿用 [多通道同步模块设计.md](./多通道同步模块设计.md) §8.5 选型：

```text
CigiIGMsgV4
  MsgID : uint16        // 指令码（含 ACK/NACK 回执编码）
  Msg   : 变长字节      // 指令参数 / 回执内容
```

**每个 IGMsg 携带两个身份标识（写死）**：


| 标识        | 字段                | 作用                                           |
| --------- | ----------------- | -------------------------------------------- |
| **MsgID** | `MsgID`（uint16）   | **指令类型**：区分「PLACEMODEL / MOVEMODEL…」，由 §2.2 编码约定决定 |
| **seq**   | `Msg` 头部（如首 2 字节） | **指令序号**：区分「同类型的第几条」，全局递增                    |


两者正交不冲突：`MsgID` 回答「这是什么命令」，`seq` 回答「这是第几条命令」。

**示例**（确认模型）：

```text
placeModel(id=1, pos=(1,2,3))  → MsgID=PLACEMODEL, seq=5
placeModel(id=1, pos=(4,5,6))  → MsgID=PLACEMODEL, seq=6   ← 同类型、不同 seq → 两条都执行
placeModel(id=1, pos=(1,2,3)) 重发 → MsgID=PLACEMODEL, seq=5（同一 seq）← 重发同一条 → IG 去重只执行一次
```



### 2.2 指令码与回执码约定

**指令码（第一版三个指令，对应 Engine 能力）**：

| MsgID 取值 | 方向 | 指令 | 含义 | 幂等性 |
|-----------|------|------|------|--------|
| `1` | Host→IG | **LOADMODEL** | 加载模型（`Msg` 携带 `.vsgt` 路径） | **幂等**（重复加载结果相同） |
| `2` | Host→IG | **PLACEMODEL** | 摆放模型（`Msg` 携带 `id + position + eulerYprDeg`） | **幂等**（设置绝对位姿，重复摆放结果相同） |
| `3` | Host→IG | **MOVEMODEL** | 累加移动模型（`Msg` 携带 `id + deltaPos + deltaYpr`，对当前 pose 累加） | **非幂等**（每次移动结果不同，重复执行会多移动一次） |

> **LOADMODEL 是 PLACEMODEL / MOVEMODEL 的基础**——模型先加载到场景，才能摆放 / 移动。三指令覆盖幂等/非幂等两类：**LOADMODEL / PLACEMODEL 幂等**，用于测「幂等指令重发安全」；**MOVEMODEL 刻意非幂等**（累加），用于测「重发同 seq 必须去重」——若去重失效，模型会多移动一次，正确性可被观测。

**回执码（两段回执，编码规则 `RECEIVED=0x7000|cmd`、`RESULT-ACK=0x8000|cmd`、`RESULT-NACK=0x9000|cmd`）**：

| MsgID 取值 | 方向 | 含义 |
|-----------|------|------|
| `0x7001` | IG→Host | RECEIVED：指令 `1`（LOADMODEL）的**收到确认**（送达，瞬时） |
| `0x7002` | IG→Host | RECEIVED：指令 `2`（PLACEMODEL）的**收到确认** |
| `0x7003` | IG→Host | RECEIVED：指令 `3`（MOVEMODEL）的**收到确认** |
| `0x8001` | IG→Host | RESULT-ACK：指令 `1`（LOADMODEL）的**执行成功**回执 |
| `0x8002` | IG→Host | RESULT-ACK：指令 `2`（PLACEMODEL）的**执行成功**回执 |
| `0x8003` | IG→Host | RESULT-ACK：指令 `3`（MOVEMODEL）的**执行成功**回执 |
| `0x9001` | IG→Host | RESULT-NACK：指令 `1`（LOADMODEL）的**执行失败**回执 |
| `0x9002` | IG→Host | RESULT-NACK：指令 `2`（PLACEMODEL）的**执行失败**回执 |
| `0x9003` | IG→Host | RESULT-NACK：指令 `3`（MOVEMODEL）的**执行失败**回执 |

**状态查询报文（第三段，RESULT 丢失/悬挂兜底）**：

| MsgID 取值 | 方向 | 含义 |
|-----------|------|------|
| `0xA000` | Host→IG | **QUERY_CMD**：查询命令 `seq` 当前状态（`Msg` 携带 seq） |
| `0xB000` | IG→Host | **CMD_STATE**：命令 `seq` 的状态应答（`Msg` 携带 seq + 状态码） |

**CMD_STATE 状态码**（`Msg` 中，实现定）：

```text
0 = 已完成（RESULT 此前已发/补发 RESULT）→ IG 同帧重发 RESULT-ACK/NACK
1 = 执行中（仍在跑，非卡死）→ Host 继续等，不误判
2 = 未知 / 未收到过该 seq（命令可能根本没送达）→ Host 走 RECEIVED 重发流程
```

**为什么需要 QUERY（写死）**：RESULT 是**一次性**报文（IG 发完默认不重发）。若 RESULT 丢失（TCP 断/对端挂/路由丢），Host 永远不知道「其实完成了」。QUERY 让 Host 主动查询，IG 重发结果——区分「完成（重发 RESULT）/ 执行中（继续等）/ 未知（重发命令）」。

> **IG 侧必须保留最近 RESULT（写死）**：QUERY 能「重发 RESULT」的前提是 IG 保留了该命令的结果。IG 侧需缓存**最近完成命令的 RESULT**（至少保留到 QUERY 应答过 / 被新命令覆盖 / 会话结束），否则 QUERY 无法补发丢失的 RESULT。这是 IG 侧新增的「结果保留」要求。

**LOADMODEL / PLACEMODEL / MOVEMODEL 的 `Msg` 载荷**（字节布局，实现定）：

```text
LOADMODEL  : [seq(2B)] [path…]                                   // 路径为变长字符串
PLACEMODEL : [seq(2B)] [id(4B)] [pos.x,y,z(3×8B)] [ypr.x,y,z(3×8B)]
MOVEMODEL  : [seq(2B)] [id(4B)] [delta.x,y,z(3×8B)] [dYaw,dPitch,dRoll(3×8B)]
```

> **移动实体 API 需求**：MOVEMODEL 的「累加」语义需要 Engine 新增能力——当前 Engine 只有读实体位姿（`sampleEntityPoseById`），**无写/移动 API**。需新增（示例签名）：
>
> ```text
> bool Engine::moveEntityById(int id, const vsg::dvec3& deltaPos, const vsg::dvec3& deltaYprDeg);
> // 读当前 pose → 累加 delta → 写回该实体 transform（本地 / 椭球按场景模式分派）
> ```
>
> 这是本设计引入的第一个「写实体」API；`hasEntityId`（存在性）已有，可作前置校验。

回执 `MsgID` 携带原命令码 + `Msg` 携带原 seq，Host 凭此关联「回执属于哪条命令、哪个阶段」（编码规则见上表）。

**回执内容（IG 业务自定）**：

- **RECEIVED**：`Msg` 只需带 seq（回显原命令 seq 即可），协议层不要求内容；
- **RESULT**：`Msg` 里装什么由 IG 业务逻辑决定——最低限度建议 `Msg` 首个字节约定 `0`=成功 / `1`=失败，其余留给业务（如错误码、进度）。**本设计不规定 RESULT 内容的完整格式**。



### 2.3 回执模型（RECEIVED / RESULT + QUERY 悬挂处理，写死）

**为什么不用「单段 ACK 等执行完」**：不同指令执行耗时差异大（复位快、加载慢），且**同一条指令**（如加载）耗时也随模型大小变化——「统一的等待超时」必然两难：设小了，慢指令正常执行却被误判超时；设大了，快指令失败要等很久。**每指令单独配阈值也不够**（同一指令耗时也是变的）。

**解法：两段回执，把「送达」和「执行完成」分开**：

```text
Host → IG：命令（MsgID + seq + payload）
IG 收到 → 立即回 RECEIVED（瞬时，只覆盖网络送达）    ← Host 用短超时等它，超时重发
IG 执行中（耗时不定，可能几秒~几十秒）…
IG 执行完 → 回 RESULT-ACK / RESULT-NACK            ← Host 不设死超时，靠悬挂检测 + QUERY 兜底
```

| 阶段 | 回执 | 等待策略 | 覆盖的问题 |
| ------ | ----------------- | ----------------------------- | --------------- |
| **送达** | RECEIVED | **短超时**（如 1~2s，只覆盖网络传输）→ 超时重发 | 「IG 没收到 / 连接断了」 |
| **执行** | RESULT-ACK / NACK | **不设死超时**；超「悬挂阈值」→ **QUERY 查询** | 「慢指令正常执行但耗时不定」 / 「RESULT 丢失」 / 「命令卡死」 |

**关键**：超时重发只针对「连 RECEIVED 都没收到」——这是唯一适合用超时判断的（瞬时响应）；RESULT 多久到取决于执行，不设死超时，慢指令不会误判。

**悬挂处理（QUERY，写死）**：RESULT 迟迟未到时，Host 不「死等」，而是发 `QUERY_CMD(seq)` 查询；IG 回 `CMD_STATE`（完成→重发 RESULT / 执行中→继续等 / 未知→重发命令，见 §2.2）。区分「慢指令正常执行」与「命令卡死」，并弥补 RESULT 丢失。

### 2.4 命令序号：全局递增 + 统一去重（写死）

**seq 的生成**：

```text
Host：seq = ++_cmdSeq（全局递增计数器，所有命令共享，单调递增）
```

**IG 侧统一去重规则（所有命令一致，不区分幂等/非幂等）**：

```text
IG 收到 IGMsg（含 MsgID, seq, payload）：
  if seq <= 已处理最大 seq（maxSeq）:
      已处理过 → 回 RECEIVED，不执行          // 重发的旧命令
  else:
      maxSeq = seq                            // ★ 收到即更新（回 RECEIVED 时），防执行中重复接受
      回 RECEIVED → 执行 → 回 RESULT-ACK/NACK
```

> **maxSeq 更新时机（写死）**：在「收到并接受」时（回 RECEIVED 时）更新，**不是**执行完才更新。原因：若执行中（RESULT 未回）Host 因 RECEIVED 丢失而重发同 seq，此时 `maxSeq` 若还没到该 seq，IG 会再次接受 → **非幂等指令（MOVEMODEL）重复执行**。收到即更新保证「执行中/已执行完」都被识别为已处理。

**幂等是什么（概念）**：

> **幂等（idempotent）= 同一个操作执行多次，效果和执行一次相同**。词源 `idem`（相同）+ `potent`（有力），借自数学 `f(f(x)) = f(x)`（作用两次 = 作用一次）。

```text
「复位」      → 执行 N 次都是回到初始状态          ← 幂等（可反复执行，结果相同）
「加载库 X」  → 重复加载结果相同（多数实现去重/覆盖）  ← 幂等
「音量 +1」   → 每次结果不同（6→7→8）               ← 非幂等
「切到下一个」 → 每次切到不同场景                     ← 非幂等
```

注意：**幂等 ≠ 只执行一次**。复位可以随时再复位（结果相同）；「不能重复执行」是另一回事。幂等说的是「重复执行的结果与执行一次相同」，不是「禁止重复执行」。

**为什么统一去重、不按幂等性区分**：

- 幂等与否是**命令类型的静态属性**（`MsgID` 决定），不是每条命令的动态标记——不需要 Host 发送时打标记；
- seq 去重对**所有命令统一做**：重发的旧命令（`seq <= maxSeq`）一律不重复执行。幂等命令去重是「优化」（结果一样，不执行更干净）；非幂等命令去重是「必须」（否则重发会多执行一次、结果错误）；
- **seq 是身份标识，不是幂等标记**：它回答「这是不是已处理过的命令」，不回答「这个命令幂不幂等」。

**示例验证**：

```text
placeModel(id=1, pos=(1,2,3)) seq=5 → 执行，maxSeq=5
placeModel(id=1, pos=(4,5,6)) seq=6 → 6>5 → 执行，maxSeq=6  （不同命令都执行）
placeModel(id=1, pos=(1,2,3)) 重发 seq=5 → 5<=6 → 去重，回 RECEIVED 不执行 （重发只执行一次）
```

**结论**：每个 IGMsg 带 `MsgID`（类型）+ `seq`（序号，全局递增）双身份；IG 用 `seq <= maxSeq` 统一去重，不区分命令是否幂等。

**已知限制：seq 为 uint16，会溢出回绕**。65535 条命令后 `++_cmdSeq` 回绕到 0，`seq <= maxSeq` 去重会把新命令误判为旧命令。周期远超单次任务（65535 条命令），**第一版不处理**（记录为已知限制；如需支撑超 6.5 万条命令的会话，后续把 seq 扩为 uint32 或对裁决做相位展开式处理）。

## 3. 传输通道：TCP 命令面



### 3.1 现状与前提缺口（必须新建）


| 现状                                                                       | 缺口                                                                                    |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------- |
| TCP 握手已通：IG `connect` → `HELLO` → Host `HELLO_ACK`，连接保留在 peer 表 / `_tcp` | **握手后无持续读写循环**：`HostSync::handleClient` 收到 HELLO 发 ACK 后即返回；`IgSync` 的 `_tcp` 仅有断线检测读 |


**本设计必须新建两侧的 TCP 命令读写循环**：

```text
Host 侧（每 peer 一条）：
  handleClient 不再立即返回，改为：
    持续读 peer 的 TCP → 解析 IGMsg（命令回执 ACK/NACK）→ 上报门面更新 InFlight（§4.3）
    从【发送队列】取命令 → 向 peer 的 TCP 写 IGMsg → 等该 peer 的 RECEIVED（超时重发）
    （sendCommand 只入队分发，非阻塞；收发在 peer 线程内，见 §4.2）

IG 侧（一条）：
  connect 后启动命令读循环（TCP 线程）：
    持续读 _tcp → 解析 IGMsg（命令）→ 回 RECEIVED → 命令入队（主线程执行，见 §5.1）
    → 收到主线程结果通知 → 回 RESULT-ACK/NACK
```



### 3.2 长度分帧（TCP 是字节流）

**CIGI CCL 不负责分帧——必须业务层自建（写死）**：

> CIGI CCL（`CigiIGMsgV4`）只做**单条完整报文**的 Pack/Unpack（字段 ↔ 字节），输入假设是「一段完整报文」；它**不处理「从 TCP 字节流里切出完整报文」**——那是传输层职责。TCP 粘包/拆包的分帧逻辑必须在业务层（本设计的命令读循环 / `CigiWire` 扩展）实现。

**CIGI V4 IGMsg 线格式（**`Pack` **输出）**：

```text
┌──────────┬──────────┬──────────┬──────────┬─────────────────┐
│ PacketSize│ PacketID │ MsgID    │ reserved │ Msg（变长，对齐） │
│ (uint16) │ (uint16) │ (uint16) │ (uint16) │                 │
└──────────┴──────────┴──────────┴──────────┴─────────────────┘
   2B          2B        2B        2B        变长（按 8 对齐）
```

- `PacketHeaderSize = 8`；`PacketSize = 8 + 对齐后 Msg 长度`；
- `seq` 放在 `Msg` 前 2 字节（§2.1）。

**业务层分帧逻辑（写死）**：

```text
命令读循环：
  1. 维护拼帧缓冲
  2. recv → 塞入缓冲
  3. 缓冲 >= 8（PacketHeaderSize）？
     → 读 PacketSize（前 2 字节）→ 知道完整长度
  4. 缓冲 >= PacketSize？
     → 取出完整一条 → 交给 CigiIGMsgV4::Unpack 解析
     → 不够 → 继续等下次 recv（拆包）
  5. 处理完一条，缓冲剩余继续（粘包）
```

`CigiBasePacket::GetPacketID()` / `GetPacketSize()` 提供字段；实现可自行拼帧缓冲。定长 `WireMsg` 握手不受影响（握手与命令读循环分层）。

### 3.3 与握手 / UDP 同步面的关系

- TCP 命令读循环**与握手错开**：握手仍是 `HELLO/HELLO_ACK`（定长 `WireMsg`），命令面用 `IGMsg`（CIGI）——同一 TCP 连接，先握手、后进入命令循环；
- UDP 同步面（IGCtrl/眼点/SOF）**不变**，与 TCP 命令面并行（[多通道同步模块设计.md](./多通道同步模块设计.md) §2 双平面）。

**读循环接管断线检测（写死）**：

- 握手 / 命令循环 / 断线检测**共用同一条 TCP 连接**（不拆多连接）；
- **命令读循环是唯一的 `recv` 者**：读到 `EOF`（`recv` 返回 0）即判定断线，联动现有 `markDisconnected()`；读到数据则分帧解析命令；
- **不再需要**现有的 `MSG_PEEK` 断线轮询（`IgSync::isTcpPeerAlive`）——读循环本身就能感知 EOF，避免**同一 socket 被两处并发读**（命令循环 `recv` + 断线检测 `MSG_PEEK` 并发读同一 fd 在 Winsock/POSIX 下不安全）。

## 4. Host 侧设计



### 4.1 API（`HostSync` 或门面 `SynchronSystem` 暴露）

```text
// 下发命令到单个 / 全体 ready IG
// 【非阻塞】：只把命令分发到各 peer 线程的发送队列，立即返回。
// RECEIVED 等待 / 超时重发在【各 peer 线程内部】完成（见 §4.2）。
bool sendCommand(std::uint16_t msgId, const std::vector<std::uint8_t>& payload);

// 命令结果回调（RESULT 阶段，peer 线程触发）
// 业务侧可注册回调：onCommandResult(igPeer, msgId, seq, ack/nack, payload)

// 命令状态查询（RESULT 未到时可查）
//   bool isCommandInFlight(seq) / getCommandResult(seq)

// 悬挂处理：RESULT 超「悬挂阈值」未到 → 发 QUERY_CMD 主动查询（§2.2）
//   bool queryCommandStatus(seq, timeoutMs)
//     IG 回 CMD_STATE：完成→补 RESULT / 执行中→继续等 / 未知→重发命令

// 业务主动放弃等待（不判失败，仅释放 Host 侧状态；IG 侧不取消执行，见 §9）
//   void cancelCommand(seq)
```



### 4.2 发送流程（写死，非阻塞分发 + 各 peer 线程独立收发）

**Host 侧线程模型**：每个 ready IG（peer）对应一个 TCP 线程（现状 `handleClient` 每 accept 一线程）。命令的「发送 + 等 RECEIVED + 重发 + 收 RESULT」**全部在各自 peer 线程内**，10 个 IG 并发、互不阻塞（总耗时 ≈ 单 RTT，不是 10 倍）。

```text
sendCommand(msgId, payload)（主线程 / 业务线程调用，非阻塞）：
  1. seq = ++_cmdSeq；组装 IGMsg{ MsgID=msgId, Msg = seq + payload }
  2. 向每个 ready IG 的 peer 线程【发送队列】入一条命令（seq, IGMsg）
  3. 立即返回（不等任何 RECEIVED / RESULT）

每个 peer 线程（各自独立）：
  A. 从自己的发送队列取命令 → 向该 IG 的 TCP 写 IGMsg
  B. 等该 seq 的 RECEIVED（receivedTimeoutMs 短超时）：
     - 收到 RECEIVED（MsgID = 0x7000|msgId，Msg 带同一 seq）→ 转入「等 RESULT」状态
     - 超时未收 RECEIVED → 重发（携带同一 seq），最多重发 N 次（如 3）
     - 重发耗尽仍未收 RECEIVED → 判定「未送达」，走业务错误处理
  C. 「等 RESULT」阶段（异步）：
     - 收到 RESULT-ACK / RESULT-NACK → 记录结果，回调 onCommandResult，释放状态
     - 超过「悬挂阈值」（commandResultSuspicionTimeoutMs）仍未收到 RESULT：
         a. 发 QUERY_CMD(seq) 查询 IG 状态
         b. CMD_STATE = 完成   → IG 重发 RESULT → 记录结果，完成
         c. CMD_STATE = 执行中 → 继续等（不误判慢指令）
         d. CMD_STATE = 未知   → 走 RECEIVED 重发流程（命令可能没送达）
         e. QUERY 反复执行中 / 业务主动放弃 → cancelCommand(seq) 释放状态
```

> **sendCommand 为什么非阻塞**：对全体 ready IG 发命令时，若主线程逐 peer「发 + 等 RECEIVED」会串行累积 10 倍 RTT。非阻塞分发让各 peer 线程并发收发，主线程不被命令面拖住。

### 4.3 命令在途记录（最小化状态表，归门面，写死）

**Host 侧不维护完整命令状态表**（不做聚合/历史），只维护**在途集合**，用于悬挂检测 / QUERY / cancelCommand：

```text
InFlight[(seq, peer)]   // 正在等 RESULT 的 (命令, IG) 对

进出时机（写死）：
  - 进：peer 线程收到该 seq 的 RECEIVED（确认送达）→ 开始等 RESULT → 记入 InFlight
  - 出：收到 RESULT-ACK / RESULT-NACK → 移出 InFlight
  - （RECEIVED 超时重发阶段「未送达」，不在 InFlight 中——那是送达阶段，不是等 RESULT）

归属：InFlight 归 SynchronSystem（门面）统一管理，线程安全。
  - peer 线程只上报事件：RESULT 到了 / RECEIVED 超时 / RECEIVED 收到
  - 门面负责：悬挂检测（扫 InFlight 中超阈值项 → 发 QUERY）、cancelCommand、isCommandInFlight 查询
  - 业务想知道各 IG 成败 → 走 onCommandResult 回调，不依赖 InFlight
```

**cancelCommand(seq) 只作用于在途 peer（写死）**：

```text
cancelCommand(seq)：
  → 遍历 InFlight 中 (seq, *) 的 peer（只有仍在等 RESULT 的）
  → 逐个移出 InFlight，标记「已放弃等待」
  → 已出集合的 peer（成功/失败）不碰——等待已结束，取消无意义
  → 不向 IG 发任何取消消息（IG 执行到底，RESULT 迟到可忽略/记录，见 §9）
```

> **部分成功、部分 in-flight 的处理**：同一条命令发到 10 个 IG，各自状态独立（有的 ACK、有的 NACK、有的 in-flight）。InFlight 按 (seq, peer) 独立记录，不聚合；`cancelCommand(seq)` 自然只作用于还在等的那几个 peer。

- **超时重发只针对 RECEIVED**（瞬时响应，阈值好定）：应对「IG 没收到 / 连接断了」；
- **RESULT 不设死超时**：慢指令（加载大模型）正常执行不会被误判超时；「悬挂阈值」只触发 QUERY 查询，不判失败；
- **RESULT-NACK 不重发**：命令本身失败（如文件不存在），重发无用，直接上报错误；
- **RESULT 丢失可弥补**：QUERY 让 IG 重发结果（RESULT 是一次性报文，丢了靠 QUERY 补）；
- **cancelCommand 只释放 Host 侧等待**，不取消 IG 侧执行（IG 执行到底，结果可迟到返回）；
- **幂等靠 seq**：重发同 seq，IG 去重（见 §2.4）。

### 4.4 peer 线程与门面的双向通道（写死）

peer 线程不能「死等 recv」——它要能：**上报事件给门面**（RECEIVED/RESULT/超时）且**接收门面指令**（发 QUERY / 取消等待）。定义两个方向的数据流：

```text
peer 线程 → 门面（事件上报，一个队列）：
  - RECEIVED 收到   → 上报 (seq, peer) → 门面把 (seq,peer) 记入 InFlight
  - RESULT 收到     → 上报 (seq, peer, ack/nack, payload) → 门面移出 InFlight + 回调 onCommandResult
  - RECEIVED 超时耗尽 → 上报 (seq, peer, 未送达) → 门面标记失败

门面 → peer 线程（指令下发，一个队列）：
  - QUERY 指令 (seq) → 通知 peer 线程向该 IG 发 QUERY_CMD
  - cancel 指令 (seq) → 通知 peer 线程放弃等 RESULT

peer 线程主循环（与 IG 侧方案 A 对称的轮询）：
  recv(sock, timeout)                      // 等 IG 回执，超时醒
  超时 → 查「门面 → peer」指令队列 → 有 QUERY/cancel 就执行 → 再查结果上报 → 回循环
  有数据 → 分帧解析（RECEIVED / RESULT / CMD_STATE）→ 上报门面 → 回循环
```

> **与 IG 侧对称**：IG 侧是「TCP 线程 + 主线程」双队列；Host 侧是「门面 + N 个 peer 线程」——每个 peer 线程同样用 **recv 超时轮询**（方案 A），既收 IG 回执，又消费「门面→peer」指令队列。第一版足够（命令低频、100ms 轮询可接受），`select` 双路监听留扩展位（§9）。

### 4.5 多 peer 处理

- 每条命令对**每个 ready IG** 独立等 RECEIVED / 收 RESULT；
- 本设计第一版**不要求齐集**（不阻塞等全部 IG 都出结果），各 peer 独立；「齐集后再开帧」为扩展位（§9）；
- **seq 全局唯一**（同一条命令发到所有 peer 携带同一 seq），IG 侧各记各的 `maxSeq`，互不冲突——无需按 peer 区分 seq；
- **InFlight 按 (seq, peer) 独立记录**（同一 seq 多 peer 各有状态，见 §4.3）。

## 5. IG 侧设计



### 5.1 执行模型：TCP 线程统一回执 + 主线程执行 + 双队列（写死）

**IG 侧命令的「接受」与「执行」分在两个线程**，避免命令执行阻塞 Engine 帧循环：

```text
TCP 命令线程（唯一网络出口，§3.1 的独立读循环）：
  - 收包 → 分帧 → 更新【命令状态表】→ 回 RECEIVED / RESULT / CMD_STATE
  - 所有回执（RECEIVED / RESULT / QUERY 应答）都由本线程发送
  - 只与主线程通过两个队列交互，不直接执行命令

主线程（Engine 帧循环 IgSync::update / preFrame）：
  - 从【命令队列】取命令 → 执行（改场景 LOAD/PLACE/MOVE）→ 结果入【结果队列】
  - 不直接回 TCP 回执，只上报执行结果

双队列（线程间解耦点，需线程安全）：
  命令队列：TCP 线程 → 主线程（待执行命令：seq + msgId + payload）
  结果队列：主线程 → TCP 线程（执行结果：seq + ack/nack + payload）
```

**命令状态表（归 TCP 线程，写死）**：

- TCP 线程维护每 seq 状态：`RECEIVED`（已回）、`EXECUTING`（已入命令队列交给主线程）、`DONE`（主线程已回结果，含 RESULT）、`UNKNOWN`（超出保留范围）；
- 主线程**不碰状态表**——只通过两个队列交互；
- 命令入队给主线程的同时，TCP 线程把状态标 `EXECUTING`。

**为什么这样划分**：
- 命令改场景（LOAD/PLACE/MOVE）必须在渲染/主线程操作（vsg 场景节点非线程安全），不能放 TCP 线程；
- 回执统一在 TCP 线程 → TCP 写无需跨线程锁，无并发写同一 socket；
- RECEIVED 在 TCP 线程收到命令时**立即回**，不依赖主线程执行进度——慢命令不会让 RECEIVED 迟到；
- QUERY 在 TCP 线程**本地查状态表自答**（§5.3），不跨线程。

### 5.2 收包流程（写死，TCP 线程）

```text
TCP 命令读循环（connect 后启动）:
  1. TCP 读 → 按 PacketID/PacketSize 拼帧 → 解析 IGMsgV4
  2. 取 MsgID + Msg（前 2 字节 = seq）
  3. 若 MsgID == QUERY_CMD（0xA000）→ 查状态表回 CMD_STATE，走 §5.3，跳过下面命令处理
     （QUERY 不参与命令去重：它是查询不是命令；重复查询无害——IG 重复应答相同状态即可）
  4. 幂等：seq <= 已处理最大 seq → 回 RECEIVED（不重复执行，见 §2.4）
  5. maxSeq = seq（收到即更新，防执行中重发重复接受）
  6. 回 RECEIVED（MsgID = 0x7000|msgId，Msg 带 seq）——立即，不等待主线程执行
  7. 命令入【命令队列】→ 状态表标 EXECUTING（交给主线程执行）
  8. 从【结果队列】收到主线程结果（seq, ack/nack）→ 状态表标 DONE → 回 RESULT-ACK/NACK
```

**结果队列消费（写死，方案 A：recv 超时轮询）**：

- **问题**：TCP 线程若「死等 recv」（Host 暂时无新命令时 recv 阻塞），主线程入队的结果（RESULT）无人消费、发不出去；
- **方案 A（第一版，写死）**：`recv` 设超时（`SO_RCVTIMEO`，如 100ms）——超时无新包则醒来，**检查结果队列**，有结果就发 RESULT，再回循环继续 recv：

```text
while (连接活着) {
    recv(sock, buf, timeout=100ms)     // 等 Host 命令，最多 100ms
    if (recv 有数据) → 分帧解析 → 处理命令（步骤 2~7）
    if (recv 超时)   → 查【结果队列】→ 有结果 → 状态表标 DONE → 回 RESULT
    → 回循环
}
```

- **为何第一版够用**：命令面低频（LOAD/PLACE/MOVE 事件驱动），RESULT 延迟 ≤ 一个超时周期（100ms）可接受（命令执行本身秒级，悬挂阈值 5000ms 远大于 100ms，不会误判）；
- **方案 B（扩展位）**：`select` 双路监听（socket 可读 + 结果队列唤醒 fd），事件驱动、RESULT 零延迟、无轮询——命令变高频或需低延迟 RESULT 时再升级，见 §9。

**主线程消费流程（帧循环 IgSync::update）**：

```text
每帧：
  1. 从【命令队列】取一条待执行命令（无则跳过）
  2. 执行（LOAD/PLACE/MOVE，改场景）
  3. 执行结果入【结果队列】（seq + ack/nack + payload）
```

> **执行与帧循环的权衡（写死）**：主线程执行慢命令会**占用当前帧的时间**——LOAD 大模型可能卡渲染一帧（帧率掉）。这是**可接受**的：命令低频、TCP 线程与回执不受影响、RECEIVED 已提前返回。「每帧取一条」指**串行处理命令**（执行完一条才处理下一条），不是分片执行。
>
> **TODO（后续）**：加载大模型导致主线程卡帧的问题，后续可用**协程/异步加载**优化（LOAD 分片到多帧、或后台线程加载 + 主线程接档），避免长任务阻塞帧循环——当前第一版不做（命令低频可容忍）。

### 5.3 状态查询（QUERY）处理（写死，TCP 线程本地自答）

**QUERY 应答不跨线程**：TCP 线程收到 QUERY_CMD 后，**查自己维护的命令状态表**即可回答，不需要与主线程通讯。

```text
TCP 线程收到 QUERY_CMD(seq) → 查状态表：
  1. 状态 DONE（RESULT 已产生并保留，见 §2.2）→ 回 CMD_STATE(seq, 完成)，并同帧重发 RESULT-ACK/NACK
  2. 状态 EXECUTING / RECEIVED（执行中或已交主线程）→ 回 CMD_STATE(seq, 执行中)
  3. 其余（从未收到 / 已被新命令覆盖 / 超出保留范围）→ 回 CMD_STATE(seq, 未知)
```

**QUERY 应答边界（写死）**：IG 只对「**正在执行的 seq**」和「**最近完成且 RESULT 仍保留的 seq**」给出明确应答（执行中 / 完成）；对**其他所有 seq**（远早于 maxSeq 的旧命令、seq 回绕后的值、从未收到的）统一回 **未知**——避免对旧/回绕 seq 答非所问（seq 回绕见 §2.4 已知限制）。

- **重发 RESULT**：弥补 RESULT 丢失（RESULT 发完即保留在状态表，丢了靠 QUERY 触发重发）；
- **执行中**：Host 继续等，不误判慢指令；
- **未知**：Host 走 RECEIVED 重发流程（命令可能根本没送达）。

- **立即回 RECEIVED**（TCP 线程收到命令即回，不依赖主线程执行进度）→ Host 靠它判定「送达」、用短超时重发；
- **RESULT 由 TCP 线程回**（收到主线程结果通知后），不设死超时；
- **必须两段都回**：RECEIVED（送达确认）+ RESULT（执行结果）缺一不可；
- **回执内容**：RECEIVED 只需带 seq；RESULT 的 `Msg` 由业务自定（最低限度首字节 0/1 表示成败，见 §2.2）；
- **断线**：IG 掉线时 TCP 命令读循环终止，Host 侧 RECEIVED 超时重发会失败（见 §9 断线策略）。

## 6. 时序

```text
正常（两段回执，双线程模型）：
Host                                       IG（TCP线程 | 主线程）
  │ sendCommand(msgId=1, "terrain.vsgt")    │
  │  seq=1, MsgID=1, Msg=[1|terrain.vsgt]  │
  │ ───────────── TCP IGMsg ──────────────▶ │  TCP线程收包
  │                                         │  TCP线程立即回 RECEIVED（不等待执行）
  │  ←──────── TCP IGMsg(RECEIVED) ──────── │  MsgID=0x7001, Msg=[seq=1]
  │  收到 RECEIVED → 送达确认 → 转等 RESULT  │
  │                                         │  TCP线程命令入队 → 主线程执行（耗时不定）
  │                                         │  主线程执行完 → 结果通知TCP线程
  │                                         │  TCP线程回 RESULT
  │  ←──────── TCP IGMsg(RESULT-ACK) ────── │  MsgID=0x8001, Msg=[1|OK]
  │  收到 RESULT-ACK → 回调 onCommandResult  │

RECEIVED 超时重发（送达失败兜底）：
  │ ────────── TCP IGMsg(seq=1) ──────────▶ │  （未回 RECEIVED）
  │  receivedTimeout 超时 → 重发 seq=1      │
  │ ────────── TCP IGMsg(seq=1) ──────────▶ │  seq<=已处理 → 回 RECEIVED（幂等）
  │  ←──────── TCP IGMsg(RECEIVED) ─────── │
  │  收 RECEIVED → 送达确认                 │

RESULT-NACK（执行失败）：
  │ ────────── TCP IGMsg(seq=1) ──────────▶ │
  │  ←──────── TCP IGMsg(RECEIVED) ─────── │  先回 RECEIVED
  │                                        │  主线程执行失败 → 通知TCP线程
  │  ←──────── TCP IGMsg(RESULT-NACK) ───── │  MsgID=0x9001（TCP线程回）
  │  收 RESULT-NACK → 不重发 → 上报错误      │

RESULT 悬挂 + QUERY 查询（RESULT 丢失 / 慢指令 / 卡死兜底）：
  │ ────────── TCP IGMsg(seq=1) ──────────▶ │
  │  ←──────── TCP IGMsg(RECEIVED) ─────── │
  │  … 超过悬挂阈值，RESULT 未到 …           │
  │ ────────── TCP IGMsg(QUERY_CMD) ──────▶ │  MsgID=0xA000, Msg=[seq=1]
  │                                        │  已执行完 → 回状态 + 重发 RESULT
  │  ←──────── TCP IGMsg(CMD_STATE) ─────── │  状态=完成
  │  ←──────── TCP IGMsg(RESULT-ACK) ────── │  重发 RESULT（弥补丢失）
  │  收 RESULT → 记录结果，完成              │
  │  或：状态=执行中 → 继续等                │
  │  或：状态=未知 → 走 RECEIVED 重发流程     │
```

## 7. 配置与 API

**配置**（可选，第一版 C++ 缺省即可，入 `SyncRoleConfig` / `HostSync`）：


| 参数                         | 含义                   | 缺省       |
| -------------------------- | -------------------- | -------- |
| `commandReceivedTimeoutMs` | 等 RECEIVED（送达确认）的短超时 | 如 1000ms |
| `commandMaxRetries`        | RECEIVED 超时重发次数上限    | 3        |
| `commandResultSuspicionTimeoutMs` | RESULT 悬挂阈值：超过则触发 QUERY 查询（**只标记不判失败**） | 如 5000ms |


> RESULT（执行结果）**无「判失败」超时**——慢指令正常执行不会被误判。`commandResultSuspicionTimeoutMs` 只用于「触发 QUERY 查询」，由 QUERY 结果区分「完成 / 执行中 / 未知」，不主动判失败（§2.3 / §4.2）。

**API 汇总**：

| API                                                  | 位置                    | 说明                                |
| ---------------------------------------------------- | --------------------- | --------------------------------- |
| `sendCommand(msgId, payload)`                       | `HostSync`（门面转发）      | 非阻塞分发命令到各 peer 线程发送队列；RECEIVED 等待/重发在 peer 线程内（§4.2） |
| `onCommand(msgId, seq, payload)`  | IG 业务回调（`IgSync` 注册）  | 命令执行（主线程从命令队列取，§5.1） |
| `queryCommandStatus(seq, timeoutMs)`                 | `HostSync`             | RESULT 悬挂时发 QUERY_CMD 查询（§4.2）   |
| `cancelCommand(seq)`                                 | `HostSync`             | 业务放弃等待（释放 Host 状态；IG 不取消执行）   |
| 命令读循环                                                | `HostSync` / `IgSync` | TCP 收 IGMsg（§3）                   |
| 测试注入/观测                                              | `IgSync`              | `lastCommandMsgId/Seq`、命令计数       |

## 8. 验收要点

对照现有测试风格（`SyncClockTests.cpp` / `HostIGTests.cpp`），标签建议：


| 场景                  | 断言要点                                                                       | 标签                       |
| ------------------- | -------------------------------------------------------------------------- | ------------------------ |
| **命令送达 + RECEIVED** | Host 发 IGMsg → IG 收到 → 立即回 RECEIVED（MsgID=0x7000|cmd，Msg 带 seq）→ Host 判定送达 | `[acceptance][bdd][e2e]` |
| **RESULT-ACK**      | IG 执行业务后回 RESULT-ACK → Host 回调成功                                           | `[acceptance][bdd][e2e]` |
| **RESULT-NACK**     | IG 业务失败回 RESULT-NACK → Host 不重发、上报错误                                       | `[acceptance][bdd][e2e]` |
| **Load → Place 顺序** | Host 先下发 LOADMODEL（加载模型）→ RESULT-ACK 后再下发 PLACEMODEL（摆放）→ IG 按序执行；断言模型先加载成功、再摆放到指定位姿（`[acceptance]` 验收 Load 是 Place/Move 基础） | `[acceptance][bdd][e2e]` |
| **RECEIVED 超时重发**   | Host 超时未收 RECEIVED → 重发（同 seq）；IG 幂等只执行一次                                  | `[acceptance][bdd][e2e]` |
| **慢指令不误判**          | IG 收到命令后长时间不执行完（模拟加载慢）：Host 已确认送达（收到 RECEIVED）、不因 RESULT 迟到而误判超时           | `[acceptance][bdd][e2e]` |
| **RESULT 丢失 → QUERY 补回** | Host 悬挂阈值触发 QUERY_CMD → IG 回 CMD_STATE=完成并重发 RESULT → Host 记录结果（弥补 RESULT 丢失） | `[acceptance][bdd][e2e]` |
| **QUERY 执行中不误判** | QUERY 回 CMD_STATE=执行中 → Host 继续等 RESULT，不判失败、不重发（防慢指令被误杀） | `[acceptance][bdd][e2e]` |
| **QUERY 未知触发重发** | QUERY 回 CMD_STATE=未知 → Host 判定「命令未送达」，走 RECEIVED 重发流程（重发命令，不傻等） | `[acceptance][bdd][e2e]` |
| **cancelCommand**     | 业务主动放弃等待 → Host 释放状态、不再等 RESULT；IG 侧执行不中断（迟到 RESULT 可忽略或记录）                  | `[unit]` / `[e2e]` |
| **幂等去重**            | 重发同 seq → IG 不回执重复执行，回 RECEIVED 不重执行（`[unit]` 注入）；**非幂等验证**：MOVEMODEL 重发同 seq 只移动一次（`sampleEntityPoseById` 断言位姿只累加一次，`[e2e]`） | `[unit]` / `[e2e]` |
| **长度分帧**            | TCP 粘包/拆包下 IGMsg 完整解析（PacketID/PacketSize）                                 | `[unit][wire-contract]`  |
| **载荷内容**            | `Msg` 携带 seq + payload，IG 解析正确                                             | `[unit]`                 |
| **断线**              | IG 掉线 → Host RECEIVED 超时重发失败 → 上报（扩展位，见 §9）                                | —                        |
| **慢命令不阻塞帧循环** | IG 执行慢命令（模拟加载大模型）期间，Engine 帧循环仍能持续 tick（update 不卡死、帧率不崩）——验证命令执行在独立线程，与帧循环解耦（§5.1） | `[acceptance][bdd][e2e]` |
| **慢命令 RECEIVED 即时** | IG 收到命令立即回 RECEIVED，即使命令执行慢/未完成——RECEIVED 不依赖主线程执行进度（§5.1） | `[acceptance][bdd][e2e]` |
| **IG 保留最近 RESULT** | QUERY 能重发 RESULT 的前提：IG 保留最近完成命令的 RESULT（直至被覆盖/会话结束）；注入验证结果保留（§2.2 / §5.3） | `[unit]` |
| **重复 QUERY 幂等** | 重复 QUERY 同一 seq 返回相同 CMD_STATE，无害（QUERY 是查询，不改变状态、不参与去重）（§5.2） | `[unit]` |
| **空闲期 RESULT 仍发出** | Host 发命令后不再发任何新包（命令面空闲），主线程执行完 → 结果队列由 TCP 线程超时轮询消费 → RESULT 仍能送达 Host（recv 超时轮询，§5.2 方案 A） | `[acceptance][bdd][e2e]` |
| **多 peer 并发命令** | Host 发一条命令到 3 个 IG：3 个 IG 都收到、各自回 RECEIVED/RESULT，互不阻塞（sendCommand 非阻塞分发，§4.2/§4.5） | `[acceptance][bdd][e2e]` |
| **cancelCommand 只作用在途** | 命令发到多 IG：部分已 RESULT、部分 in-flight → cancelCommand(seq) 只取消在途的 peer（InFlight 按 (seq, peer)，§4.3）；已出集合的 peer 不碰 | `[acceptance][bdd][e2e]` |
| **门面↔peer 双向通道** | peer 线程能上报 RECEIVED/RESULT 给门面（更新 InFlight），且能接收门面 QUERY/cancel 指令（recv 超时轮询，§4.4）——空闲期门面发 QUERY，peer 线程超时醒后执行 | `[acceptance][bdd][e2e]` |

| **IG 侧取消执行（CANCEL 指令）**  | **扩展位**（第一版只做 Host 侧 `cancelCommand` 放弃等待，IG 执行到底） | 需要中断长任务（如停止加载）时                              |
