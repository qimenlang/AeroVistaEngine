# 状态同步设计·初版（最小可用第一版）

> **本版为「最小可用第一版」**，当前要实现的版本。完整设计（QUERY 悬挂查询、cancelCommand、双线程执行、多 peer 并发等）见 [状态同步设计.md](./状态同步设计.md)（完整版，暂不实现）。

面向本项目 **1 Host + 多 IG** 的命令面最小闭环：Host 通过 **TCP 命令面**向各 IG 下发指令（LOADMODEL / PLACEMODEL / MOVEMODEL），IG 执行后沿同一条 TCP 回执 ACK/NACK。

**一句话**：命令走 **TCP 命令面**，载荷用 **CIGI `IGMsg`（V4）**；IG 收到命令**立即回 RECEIVED**（送达确认，短超时），**执行完再回 RESULT**（ACK/NACK）；命令带 **seq** 保证幂等。

## 1. 范围与目标

| 纳入初步 | 暂不纳入 |
|----------|----------|
| Host 组装 `IGMsg` → TCP 下发 | QUERY / CMD_STATE 悬挂查询 |
| IG 收命令 → 回 RECEIVED → 执行 → 回 RESULT | cancelCommand / 在途集合 |
| Host 等 RECEIVED 短超时确认（超时即失败） | 双线程执行模型（单线程串行即可） |
| seq 幂等去重 | 多 peer 并发分发（串行即可） |
| TCP 命令读写循环 | 多通道齐集 |
| 长度分帧 / 断线检测 | 命令队列 / 优先级 |

**目标**：跑通「Host 发指令 → IG 确认收到 → IG 执行 → 回结果 → Host 判定」的最小闭环。

**关键认知**：命令「执行与否」必须有答案（ACK/NACK）；「送达」用 RECEIVED 短超时确认兜底。

## 2. 报文与协议

### 2.1 载荷：CIGI `IGMsg`（V4）

沿用 [多通道同步模块设计.md](./多通道同步模块设计.md) §8.5 选型。

```text
CigiIGMsgV4
  MsgID : uint16        // 指令码（含回执编码）
  Msg   : 变长字节      // seq(2B) + 载荷
```

**双身份标识**：`MsgID` = 指令类型；`Msg` 前 2 字节 = `seq`（指令序号，全局递增）。

### 2.2 指令码与回执码

| MsgID | 方向 | 指令 | 含义 | 幂等性 |
|-------|------|------|------|--------|
| `0x0001` | Host→IG | **LOADMODEL** | 加载模型（路径） | 幂等 |
| `0x0002` | Host→IG | **PLACEMODEL** | 摆放模型（id + 绝对位姿） | 幂等 |
| `0x0003` | Host→IG | **MOVEMODEL** | 累加移动（id + delta） | **非幂等** |

**回执码（编码规则 `RECEIVED=0x7000\|cmd`、`RESULT-ACK=0x8000\|cmd`、`RESULT-NACK=0x9000\|cmd`）**：

| MsgID | 方向 | 含义 |
|-------|------|------|
| `0x7001~0x7003` | IG→Host | RECEIVED：指令 `0x0001~0x0003` 的收到确认 |
| `0x8001~0x8003` | IG→Host | RESULT-ACK：指令 `0x0001~0x0003` 执行成功 |
| `0x9001~0x9003` | IG→Host | RESULT-NACK：指令 `0x0001~0x0003` 执行失败 |

> 回执 `MsgID = 高位基码 \| 指令码`（如 `0x8000 \| 0x0002 = 0x8002`），Host 凭回执 `MsgID` 反推对应指令。

**载荷布局**（本机字节序，两端 Windows x86 一致，`memcpy` 填/读）：

```text
LOADMODEL  : [seq(2B)] [path…]
PLACEMODEL : [seq(2B)] [id(4B)] [pos(3×8B)] [ypr(3×8B)]
MOVEMODEL  : [seq(2B)] [id(4B)] [delta(3×8B)] [dYpr(3×8B)]
```

### 2.3 命令序号：全局递增 + 统一去重

```text
Host：seq = ++_cmdSeq（全局递增）

IG 收到 IGMsg（MsgID, seq, payload）：
  if seq <= maxSeq:        // 已处理过（含执行中）
      回 RECEIVED，不执行   // 重发幂等
  else:
      maxSeq = seq         // 收到即更新，防执行中重发重复接受
      回 RECEIVED → 执行 → 回 RESULT
```

**已知限制**：seq 为 uint16，65535 条后回绕——第一版不处理（远超单次任务）。

## 3. 传输通道：TCP 命令面

### 3.1 现状与前提缺口

| 现状 | 缺口 |
|------|------|
| TCP 握手已通（HELLO/HELLO_ACK），连接保留在 peer 表 / `_tcp` | 握手后无持续读写循环，需新建 |

**本设计必须新建两侧的 TCP 命令读写循环**：

```text
Host 侧（每 peer 一条）：
  handleClient 不再立即返回：
    持续读 peer 的 TCP → 解析 IGMsg（RECEIVED/RESULT）→ 处理
    sendCommand()：向 peer 的 TCP 写 IGMsg

IG 侧（一条）：
  connect 后启动命令读循环：
    持续读 _tcp → 解析 IGMsg（命令）→ 回 RECEIVED → 执行 → 回 RESULT
```

### 3.2 长度分帧（TCP 是字节流）

CIGI CCL 只做单条报文 Pack/Unpack，**不做 TCP 流分帧——必须业务层自建**。

```text
CIGI V4 IGMsg 线格式（Pack 输出）：
┌──────────┬──────────┬──────────┬──────────┬─────────────────┐
│ PacketSize│ PacketID │ MsgID    │ reserved │ Msg（变长，对齐） │
└──────────┴──────────┴──────────┴──────────┴─────────────────┘
   2B          2B        2B        2B        变长（按 8 对齐）

分帧逻辑：
  1. 维护拼帧缓冲
  2. recv → 塞入缓冲
  3. 缓冲 >= 8？→ 读 PacketSize → 知完整长度
  4. 缓冲 >= PacketSize？→ 取完整一条 → CigiIGMsgV4::Unpack
  5. 剩余继续（粘包/拆包都覆盖）
```

### 3.3 断线检测

- 命令读循环是唯一 `recv` 者：读到 EOF（`recv` 返回 0）即判定断线，联动现有 `markDisconnected()`；
- 不再需要现有 `MSG_PEEK` 轮询（避免同一 socket 两处并发读）；
- 物理断网（无 FIN/RST）时 `recv` 卡住，需 `recv` 超时或心跳兜底（[socket总结.md](../notes/socket总结.md) §5.1）。

## 4. 执行模型：单线程串行

**第一版用单线程串行执行，不做双线程**：

```text
IG 命令读循环（connect 后启动，单线程）：
  收到命令 → 回 RECEIVED → 就地执行（LOAD/PLACE/MOVE）→ 回 RESULT → 处理下一条
```

- 命令低频、事件驱动（LOAD/PLACE/MOVE 不是每帧发），串行足够；
- **权衡**：慢命令（LOAD 大模型）会阻塞该线程——第一版可接受（命令低频）；若后续卡帧不可接受，用协程/异步加载优化（见 §10）；
- 多 peer：Host 每 peer 一条 `handleClient` 线程（现状），各 IG 独立收发；`sendCommand` 对 ready IG 逐个发（串行即可，第一版）。

## 5. Host 侧设计

### 5.1 API

```text
// 下发命令到单个 / 全体 ready IG
// 阻塞等 RECEIVED（缺省 1000ms）；超时即判定「未送达」。
bool sendCommand(std::uint16_t msgId, const std::vector<std::uint8_t>& payload,
                 std::uint32_t receivedTimeoutMs = 1000);

// 命令结果回调（RESULT 阶段）
void onCommandResult(igPeer, msgId, seq, ack/nack, payload);
```

> **第一版 `sendCommand` 阻塞等 RECEIVED**（串行逐 peer），简单直接。10 个 IG 串行 RTT 累积可接受（命令低频）；多 peer 并发分发留扩展位。
>
> **阻塞等 RECEIVED 的唤醒机制（写死）**：`sendCommand` 在业务线程阻塞等 RECEIVED，而 RECEIVED 由 peer 线程（`handleClient` 读循环）收到。两者用**条件变量/事件 + 超时等待**同步：
>
> ```text
> sendCommand 等 RECEIVED（业务线程）：
>   cv.wait_for(timeout)   // 等 peer 线程通知，或超时
> peer 线程收到 RECEIVED：
>   更新状态 → cv.notify()  // 唤醒等该 seq RECEIVED 的业务线程
> ```
>
> - 用「**每命令一个等待事件**」（或按 seq 匹配），避免串命令的 RECEIVED 互相误唤醒；
> - `cv.wait_for(receivedTimeoutMs)` 超时即「未送达」。

### 5.2 发送流程

```text
sendCommand(msgId, payload, receivedTimeoutMs=1000):
  1. seq = ++_cmdSeq；组装 IGMsg{ MsgID=msgId, Msg = seq + payload }
  2. 对每个 ready IG（串行）：TCP 写 IGMsg
  3. 等该 seq 的 RECEIVED（receivedTimeoutMs 短超时）：
     - 收到 RECEIVED → 转入「等 RESULT」，返回
     - 超时未收 RECEIVED → 判定「未送达」，走业务错误处理（不重发）
  4. 等 RESULT（异步，peer 线程内）：
     - 收到 RESULT-ACK/NACK → 回调 onCommandResult
     - 无超时判失败（慢指令不误判）
```

> **为什么不做「重发 N 次」、超时即失败（写死）**：TCP 层已保证字节送达；「没收到 RECEIVED」只剩 IG 进程挂了 / 连接僵死——重发多少次都没用（IG 不会活过来）。即使 RECEIVED 恰好丢包（TCP 下几乎不发生），Host 重发一次 + IG 幂等也能兜住。故**只保留 `commandReceivedTimeoutMs`，不设重发次数上限**。

- **RECEIVED 超时即判定失败**（瞬时响应，阈值好定，不做重发次数上限，见上）；
- **RESULT 不设超时**：慢指令（加载大模型）不误判；
- **NACK 不重发**：命令本身失败，重发无用；
- **幂等靠 seq**：若实现仍重发（如未来加次数上限），重发同 seq 被 IG 去重。

## 6. IG 侧设计

### 6.1 API

```text
// 命令读循环收 IGMsg → 分发
void onCommand(msgId, seq, payload, ReplyFn reply);   // 业务执行，reply 回 RESULT

// 测试观测：lastCommandMsgId() / lastCommandSeq() / 命令计数
```

### 6.2 收包流程

```text
命令读循环（connect 后启动）:
  1. TCP 读 → 按 PacketID/PacketSize 拼帧 → 解析 IGMsgV4
  2. 取 MsgID + Msg（前 2 字节 = seq）
  3. 幂等：seq <= maxSeq → 回 RECEIVED（不重复执行）
  4. maxSeq = seq（收到即更新）
  5. 回 RECEIVED（MsgID = 0x7000 | 指令码，如 0x7001；Msg 带 seq）——立即
  6. 执行命令（LOAD/PLACE/MOVE）
  7. 执行完 → 回 RESULT-ACK/NACK
```

- 立即回 RECEIVED（送达确认），执行完回 RESULT（耗时不定）；
- 两段都回，缺一不可；
- **串行执行的 RECEIVED 延迟（写死）**：单线程串行执行时，慢命令（LOAD 大模型）期间，后续命令的 RECEIVED 会**延迟**（前一条执行完才处理下一条）。Host 的 RECEIVED 短超时可能因此**误判「未送达」**——但这是可接受的：`receivedTimeoutMs` 取保守值（如 1000ms）容忍串行延迟，且即使误判，业务可重发（幂等兜住，不重复执行）；
- 断线：读循环终止，Host RECEIVED 超时失败。

## 7. 时序

```text
Host                                      IG
  │ sendCommand(0x0001, "terrain.vsgt")    │
  │  seq=1, MsgID=0x0001, Msg=[1|path…]   │
  │ ───────────── TCP IGMsg ─────────────▶ │  命令读循环收包
  │                                        │  立即回 RECEIVED（不等待执行）
  │  ←──────── TCP IGMsg(RECEIVED) ─────── │  MsgID=0x7001, Msg=[seq=1]
  │  收到 RECEIVED → 送达确认 → 转等 RESULT │
  │                                        │  执行（耗时不定）
  │                                        │  执行完回 RESULT
  │  ←──────── TCP IGMsg(RESULT-ACK) ───── │  MsgID=0x8001, Msg=[1|OK]
  │  收到 RESULT-ACK → 回调 onCommandResult │

RECEIVED 超时（未送达）：
  │ ────────── TCP IGMsg(seq=1) ──────────▶ │  （未回 RECEIVED）
  │  timeout → 判定「未送达」，走业务错误处理 │
  │  （若业务选择重发，IG 幂等兜住：）        │
  │  ────────── TCP IGMsg(seq=1) ──────────▶ │  seq<=已处理 → 回 RECEIVED（不重复执行）
  │  ←──────── TCP IGMsg(RECEIVED) ─────── │
```

## 8. 配置与 API

| 参数 | 含义 | 缺省 |
|------|------|------|
| `commandReceivedTimeoutMs` | 等 RECEIVED 的短超时；**超时即判定「未送达」**（不做重发次数上限，见 §5.2） | **1000ms**（`sendCommand` 缺省值） |

> **为什么保留 `commandReceivedTimeoutMs`、舍弃 `commandMaxRetries`**：超时是必要的——没有它，IG 挂了 / 连接僵死时 Host 会永远等 RECEIVED。但**重发次数上限不需要**——TCP 保证字节送达，超时的根因（IG 挂/连接断）重发无效，一次超时即失败即可。**第一版先用缺省值**：`sendCommand(msgId, payload, /*receivedTimeoutMs=*/1000)`，配置项入 JSON 留扩展位。

| API | 位置 | 说明 |
|-----|------|------|
| `sendCommand(msgId, payload, receivedTimeoutMs=1000)` | `HostSync` | 下发 + 等 RECEIVED（缺省 1000ms）；超时即失败 |
| `onCommand(msgId, seq, payload, reply)` | `IgSync` | 命令执行 + 回 RESULT |
| 命令读循环 | `HostSync` / `IgSync` | TCP 收 IGMsg |
| 测试注入/观测 | `IgSync` | `lastCommandMsgId/Seq`、命令计数 |

## 9. 验收要点

| 场景 | 断言要点 | 标签 |
|------|----------|------|
| 命令送达 + RECEIVED | Host 发 → IG 收到 → 回 RECEIVED → Host 判定送达 | `[acceptance][bdd][e2e]` |
| RESULT-ACK / NACK | IG 执行后回 RESULT → Host 回调成功/失败 | `[acceptance][bdd][e2e]` |
| Load → Place 顺序 | 先 LOAD 后 PLACE，按序执行 | `[acceptance][bdd][e2e]` |
| RECEIVED 超时 | 超时未收 RECEIVED → 判定「未送达」；若重发，IG 幂等只执行一次 | `[acceptance][bdd][e2e]` |
| 幂等去重 | 重发同 seq → IG 不重复执行；MOVEMODEL 重发只移动一次 | `[unit]` / `[e2e]` |
| 长度分帧 | 粘包/拆包下 IGMsg 完整解析 | `[unit][wire-contract]` |
| 载荷内容 | `Msg` 携带 seq + payload，解析正确 | `[unit]` |
| 慢指令不误判 | 慢命令 RESULT 迟到，Host 不判失败 | `[acceptance][bdd][e2e]` |
| 断线 | IG 掉线 → Host RECEIVED 超时失败 → 上报 | — |
