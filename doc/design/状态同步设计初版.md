# 状态同步设计·初版（最小可用第一版）

> **本版为「最小可用第一版」**，当前要实现的版本。完整设计（QUERY 悬挂查询、cancelCommand、多 peer 并发等）见 [状态同步设计.md](./状态同步设计.md)（完整版，暂不实现）。

面向本项目 **1 Host + 多 IG** 的命令面最小闭环：Host 通过 **TCP 命令面**向各 IG 下发指令（LOADMODEL / PLACEMODEL / MOVEMODEL），IG 执行后沿同一条 TCP 回执 ACK/NACK。

**一句话**：命令走 **TCP 命令面**，载荷用 **CIGI `IGMsg`（V4）**；IG 收到命令**立即回 RECEIVED**（送达确认，短超时），**执行完再回 RESULT**（ACK/NACK）；命令带 **seq** 保证幂等。

## 1. 范围与目标

| 纳入初步 | 暂不纳入 |
|----------|----------|
| Host 组装 `IGMsg` → TCP 下发 | QUERY / CMD_STATE 悬挂查询 |
| IG 收命令 → 回 RECEIVED → 执行 → 回 RESULT | cancelCommand / 在途集合 |
| Host 等 RECEIVED 短超时确认（超时即失败） | 多 peer 并发分发（串行即可） |
| seq 幂等去重 | 多通道齐集 |
| TCP 命令读写循环 | 命令队列 / 优先级 |
| 长度分帧 / 断线检测 | — |
| **命令读循环线程 + 主线程执行**（回执/执行解耦，见 §4） | — |

**目标**：跑通「Host 发指令 → IG 确认收到 → IG 执行 → 回结果 → Host 判定」的最小闭环。

**关键认知**：命令「执行与否」必须有答案（ACK/NACK）；「送达」用 RECEIVED 短超时确认兜底。

## 2. 报文与协议

### 2.1 载荷：CIGI `IGMsg`（V4）

沿用 [多通道同步模块设计.md](./多通道同步模块设计.md) §8.5 选型。

```text
CigiIGMsgV4
  MsgID : uint16        // 指令码（含回执编码）
  Msg   : 变长字节      // seq(2B) + 载荷
```

**双身份标识**：`MsgID` = 指令类型；`Msg` 前 2 字节 = `seq`（指令序号，全局递增）。

### 2.2 指令码与回执码

| MsgID | 方向 | 指令 | 含义 | 幂等性 |
|-------|------|------|------|--------|
| `0x0001` | Host→IG | **LOADMODEL** | 加载模型（id + 路径） | 幂等 |
| `0x0002` | Host→IG | **PLACEMODEL** | 摆放模型（id + 绝对位姿） | 幂等 |
| `0x0003` | Host→IG | **MOVEMODEL** | 累加移动（id + delta） | **非幂等** |

**回执码（编码规则 `RECEIVED=0x7000\|cmd`、`RESULT-ACK=0x8000\|cmd`、`RESULT-NACK=0x9000\|cmd`）**：

| MsgID | 方向 | 含义 |
|-------|------|------|
| `0x7001~0x7003` | IG→Host | RECEIVED：指令 `0x0001~0x0003` 的收到确认 |
| `0x8001~0x8003` | IG→Host | RESULT-ACK：指令 `0x0001~0x0003` 执行成功 |
| `0x9001~0x9003` | IG→Host | RESULT-NACK：指令 `0x0001~0x0003` 执行失败 |

> 回执 `MsgID = 高位基码 \| 指令码`（如 `0x8000 \| 0x0002 = 0x8002`），Host 凭回执 `MsgID` 反推对应指令。

**载荷布局**（本机字节序，两端 Windows x86 一致，`memcpy` 填/读）：

```text
LOADMODEL  : [seq(2B)] [id(4B)] [path…]
PLACEMODEL : [seq(2B)] [id(4B)] [pos(3×8B)] [ypr(3×8B)]
MOVEMODEL  : [seq(2B)] [id(4B)] [delta(3×8B)] [dYpr(3×8B)]
```

> **LOAD 的实体 id（写死）**：LOADMODEL 载荷携带 `id(4B)`（与 PLACEMODEL 一致，由 Host 决定实体 id）。IG 侧执行时用该 id 组装 `Entity{id, path, node}` 放入实体表；后续 `PLACEMODEL(同 id)` 升级该实体位姿（挂 node 到 transform）。`PLACEMODEL` 目标 id 必须**已存在**（LOAD 已建或配置已加载），否则执行失败回 RESULT-NACK。LOAD/PLACE 的实体状态收敛于 IG 引擎实体表，无旁路缓存。

### 2.3 命令序号：全局递增 + 统一去重

```text
Host：seq = ++_cmdSeq（全局递增）

IG 收到 IGMsg（MsgID, seq, payload）：
  if seq <= maxSeq:        // 已处理过（含执行中）
      回 RECEIVED，不执行   // 重发幂等
  else:
      maxSeq = seq         // 收到即更新，防执行中重发重复接受
      回 RECEIVED → 执行 → 回 RESULT
```

**已知限制**：seq 为 uint16，65535 条后回绕——第一版不处理（远超单次任务）。

## 3. 传输通道：TCP 命令面

### 3.1 现状与前提缺口

| 现状 | 缺口 |
|------|------|
| TCP 握手已通（HELLO/HELLO_ACK），连接保留在 peer 表 / `_tcp` | 握手后无持续读写循环，需新建 |

**本设计必须新建两侧的 TCP 命令读写循环**：

```text
Host 侧（每 peer 一条）：
  handleClient 不再立即返回：
    持续读 peer 的 TCP → 解析 IGMsg（RECEIVED/RESULT）→ 处理
    sendCommand()：向 peer 的 TCP 写 IGMsg

IG 侧（一条命令读循环线程）：
  connect 成功后启动**独立线程**（不是帧循环 update 驱动）：
    持续读 _tcp → 解析 IGMsg（命令）→ 回 RECEIVED → 命令入队 → 主线程执行回 RESULT
```

> **UDP 接收收敛（写死）**：Host 侧 UDP 接收由后台 `_udpThread`（每 2ms `pollUdp`）**独占**，引擎帧循环不再 poll（`HostSync::update` 只发不收）；IG 侧 `update` 只在帧内收 IGCtrl（帧同步语义，必须按帧消费）并发 SOF。断线检测（TCP）并入 IG 命令读循环线程（§3.3）。

### 3.2 长度分帧（TCP 是字节流）

CIGI CCL 只做单条报文 Pack/Unpack，**不做 TCP 流分帧——必须业务层自建**。

```text
CIGI V4 IGMsg 线格式（Pack 输出）：
┌──────────┬──────────┬──────────┬──────────┬─────────────────┐
│ PacketSize│ PacketID │ MsgID    │ reserved │ Msg（变长，对齐） │
└──────────┴──────────┴──────────┴──────────┴─────────────────┘
   2B          2B        2B        2B        变长（按 8 对齐）

分帧逻辑：
  1. 维护拼帧缓冲
  2. recv → 塞入缓冲
  3. 缓冲 >= 8？→ 读 PacketSize → 知完整长度
  4. 缓冲 >= PacketSize？→ 取完整一条 → CigiIGMsgV4::Unpack
  5. 剩余继续（粘包/拆包都覆盖）
```

### 3.3 断线检测

- 命令读循环是唯一**消费数据**的 `recv` 者：读到 EOF（`recv` 返回 0）即判定断线，联动 `markDisconnected()`（**TCP 存活检测并入命令读循环线程**，`update` 帧内不再 MSG_PEEK 探活）；
- 物理断网（无 FIN/RST）时 `recv` 卡住，需 `recv` 超时或心跳兜底（[socket总结.md](../notes/socket总结.md) §5.1）；命令读循环的 `SO_RCVTIMEO`（100ms）超时唤醒可作弱心跳，但静默断网仍依赖外部心跳（扩展位）；

### 3.4 断线行为（写死，第一版「断线即失败」）

- **Host 等待中的 RECEIVED/RESULT**：断线后回执不再到达，`sendCommand` 等 RECEIVED **超时即判定「未送达」失败**（§5.2）；等 RESULT 的 `onCommandResult` 不回调（命令视为未完成）；
- **IG 重连后的 seq 状态**：`maxSeq` 是**会话内状态**，重连（新会话）后**从 0 重新开始**（类比时钟同步的 `resetHostSession`）；
- **未完成命令**：不重发——断线后命令重连重发为扩展位（§10）。

## 4. 执行模型：命令读循环线程 + 主线程执行

**第一版采用「命令读循环线程回 RECEIVED + 主线程执行命令」**：

```text
IG 命令读循环线程（connect 成功后启动，独立线程）：
  收到命令 → 幂等检查 → 观测记录 → 回 RECEIVED（可延迟）→ 命令入队 → 处理下一条

IG 主线程（帧循环，SynchronSystem::update → runPendingCommands）：
  取队首命令 → 执行（LOAD/PLACE/MOVE）→ 回 RESULT → 下一条
```

> **读循环线程模型（写死）**：IG 命令读循环是 **connect 成功后启动的独立线程**，**不是**帧循环 `update` 驱动。理由：`sendCommand` 在 Host 业务线程**阻塞等 RECEIVED**，若 IG 收包靠帧循环驱动，则阻塞期间 IG 无人收包，RECEIVED 永不回。读循环线程成为 IG 侧 TCP 唯一 `recv` 者（§3.3），`update` 不再 poll TCP。
>
> **执行归主线程（写死，实机崩溃驱动）**：命令执行（LOAD/PLACE/MOVE → 改场景 `addChild`、`transform->matrix`、`_viewer->compile()`）**必须在 IG 主线程**（帧循环 `runPendingCommands`）执行，**不另起执行线程**。原因：场景图与 GPU 对象只允许渲染线程侧修改——独立执行线程改场景会与渲染遍历并发（`vsg::Children` 越界）且新挂载节点 pipeline 未编译（`GraphicsPipeline::vk()` 越界），实测双双崩溃（见 §6.2）。主线程执行使改场景与渲染天然串行，无需锁。
>
> **观测与回执解耦**：`commandCount`/`lastCommandMsgId/Seq` 在**收到命令时**（读循环线程）记录，不依赖主线程执行完成；RESULT 由主线程执行后回（`runPendingCommands`）。

- 命令低频事件驱动，主线程每帧取一条执行（保序：LOAD 先于 PLACE）；
- **权衡**：慢命令（LOAD 大模型）阻塞主线程一帧（帧率掉一次）——可接受（命令低频、一帧卡顿可容忍）；RECEIVED 仍由读循环线程即时回，Host 不误判；若卡帧不可接受，用协程/异步加载优化（见 §10）；
- 多 peer：Host 每 peer 一条 `handleClient` 线程（现状），各 IG 独立收发；`sendCommand` 对 ready IG 逐个发（串行即可，第一版）。

## 5. Host 侧设计

### 5.1 API

```text
// 下发命令到单个 / 全体 ready IG
// 阻塞等 RECEIVED（缺省 1000ms）；超时即判定「未送达」。
bool sendCommand(cigi_wire::Command cmd, const std::vector<std::uint8_t>& payload,
                 std::uint32_t receivedTimeoutMs = 1000);

// 命令结果回调（RESULT 阶段）
void setCommandResultCallback(bool ack, std::uint16_t seq, cigi_wire::Command cmd);
```

> **第一版 `sendCommand` 阻塞等 RECEIVED**（串行逐 peer），简单直接。10 个 IG 串行 RTT 累积可接受（命令低频）；多 peer 并发分发留扩展位。
>
> **阻塞等 RECEIVED 的唤醒机制（写死）**：`sendCommand` 在业务线程阻塞等 RECEIVED，而 RECEIVED 由 peer 线程（`handleClient` 读循环）收到。两者用**条件变量/事件 + 超时等待**同步：
>
> ```text
> sendCommand 等 RECEIVED（业务线程）：
>   cv.wait_for(timeout)   // 等 peer 线程通知，或超时
> peer 线程收到 RECEIVED：
>   更新状态 → cv.notify()  // 唤醒等该 seq RECEIVED 的业务线程
> ```
>
> - 用「**每命令一个等待事件**」（或按 seq 匹配），避免串命令的 RECEIVED 互相误唤醒；
> - `cv.wait_for(receivedTimeoutMs)` 超时即「未送达」。

### 5.2 发送流程

```text
sendCommand(cmd, payload, receivedTimeoutMs=1000) → bool：
  1. seq = ++_cmdSeq；组装 IGMsg{ MsgID=cmd, Msg = seq + payload }
  2. 快照当前 ready IG 列表；**无 ready peer → 返回 false**（无 peer 收到命令）
  3. 对快照逐个（串行）：TCP 写 IGMsg → 等该 seq 的 RECEIVED（receivedTimeoutMs 短超时）
     - 收到 RECEIVED → 继续下一个
     - 超时未收 RECEIVED → 判定「未送达」，**返回 false**（不重发）
  4. 全部 ready peer 均收到 RECEIVED → 返回 true（转入「等 RESULT」）
  5. 等 RESULT（异步，peer 线程内）：
     - 收到 RESULT-ACK/NACK → 回调 setCommandResultCallback
     - 无超时判失败（慢指令不误判）
```

> **返回值语义（写死）**：`sendCommand` 返回 **「本轮所有 ready peer 是否都收到 RECEIVED」**——任一 peer 超时未送达即返回 false（含「无 ready peer」）。断线场景（§3.4）下，IG 掉线使 RECEIVED 不达，返回值必然为 false；即使 Host 读循环恰好已感知断线并从 ready 列表移除该 peer，无 ready peer 同样返回 false——两种时序下语义一致。

> **为什么不做「重发 N 次」、超时即失败（写死）**：TCP 层已保证字节送达；「没收到 RECEIVED」只剩 IG 进程挂了 / 连接僵死 / 读循环被慢命令阻塞——重发多少次都没用（IG 不会活过来 / 不会加快回执）。故**只保留 `commandReceivedTimeoutMs`，不设重发次数上限**。
>
> **初版无「同 seq 重发」接口（写死）**：`sendCommand` 每次调用 `seq = ++_cmdSeq`，业务重发即**新 seq 的新命令**（IG 会执行，MOVEMODEL 尤其有害），业务需自行评估是否重发。IG 侧 `seq <= maxSeq` 幂等（§2.3）仍须实现——它防护的是**未来**引入同 seq 重发（扩展位）时 IG 不重复执行，也供注入测试验证 IG 侧去重逻辑。

- **RECEIVED 超时即判定失败**（瞬时响应，阈值好定，不做重发次数上限，见上）；
- **RESULT 不设超时**：慢指令（加载大模型）不误判；
- **NACK 不重发**：命令本身失败，重发无用；
- **幂等靠 seq**：IG 侧 `seq <= maxSeq` 去重（§2.3）防未来同 seq 重发重复执行；初版无同 seq 重发接口，业务重发即新命令。

## 6. IG 侧设计

### 6.1 API

```text
// 业务执行回调：返回 true=成功（回 RESULT-ACK），false=失败（回 RESULT-NACK）
bool setCommandHandler(cigi_wire::Command cmd, std::uint16_t seq,
                       const std::vector<std::uint8_t>& payload);

// 测试观测：lastCommandMsgId() / lastCommandSeq() / commandCount()
```

### 6.2 收包流程

```text
命令读循环线程（connect 成功后启动的独立线程）:
  1. TCP 读 → 按 PacketID/PacketSize 拼帧 → 解析 IGMsgV4
  2. 取 MsgID + Msg（前 2 字节 = seq）
  3. 幂等：seq <= maxSeq → 回 RECEIVED（不重复执行）
  4. maxSeq = seq（收到即更新）
  5. 观测记录（lastCommandMsgId/Seq、命令计数）——收到即记
  6. 回 RECEIVED（MsgID = 0x7000 | 指令码，如 0x7001；Msg 带 seq）——立即（可注入延迟）
  7. 命令入队 → 主线程取走

主线程（帧循环，runPendingCommands）:
  8. 取队首命令 → 执行（LOAD/PLACE/MOVE）→ 回 RESULT-ACK/NACK
```

- 立即回 RECEIVED（送达确认，命令读循环线程），执行完回 RESULT（主线程帧内，耗时不定）；两段都回，缺一不可；
- **RECEIVED 与执行解耦（写死，§4）**：命令执行归主线程（场景归属主线程，避免跨线程改场景/pipeline 编译崩溃）；读循环线程只负责收包回执，不被慢命令阻塞——后续命令的 RECEIVED 不延迟（避免 Host 短超时误判「未送达」）；观测在**收到时**记录，不依赖执行完成；
- 慢命令（LOAD 大模型）阻塞主线程一帧：帧率掉一次可接受（命令低频），RESULT 随该帧回；
- 断线：命令读循环终止，Host RECEIVED 超时失败。

## 7. 时序

```text
Host                                      IG
  │ sendCommand(0x0001, "terrain.vsgt")    │
  │  seq=1, MsgID=0x0001, Msg=[1|path…]   │
  │ ───────────── TCP IGMsg ─────────────▶ │  命令读循环收包
  │                                        │  立即回 RECEIVED（不等待执行）
  │  ←──────── TCP IGMsg(RECEIVED) ─────── │  MsgID=0x7001, Msg=[seq=1]
  │  收到 RECEIVED → 送达确认 → 转等 RESULT │
  │                                        │  执行（耗时不定）
  │                                        │  执行完回 RESULT
  │  ←──────── TCP IGMsg(RESULT-ACK) ───── │  MsgID=0x8001, Msg=[1|OK]
  │  收到 RESULT-ACK → 回调 onCommandResult │

RECEIVED 超时（未送达）：
  │ ────────── TCP IGMsg(seq=1) ──────────▶ │  （未回 RECEIVED）
  │  timeout → 判定「未送达」，走业务错误处理 │
  │  （未来同 seq 重发为扩展位，IG 幂等兜住：）│
  │  ────────── TCP IGMsg(seq=1) ──────────▶ │  seq<=已处理 → 回 RECEIVED（不重复执行）
  │  ←──────── TCP IGMsg(RECEIVED) ─────── │
```

## 8. 配置与 API

| 参数 | 含义 | 缺省 |
|------|------|------|
| `commandReceivedTimeoutMs` | 等 RECEIVED 的短超时；**超时即判定「未送达」**（不做重发次数上限，见 §5.2） | **1000ms**（`sendCommand` 缺省值） |

> **为什么保留 `commandReceivedTimeoutMs`、舍弃 `commandMaxRetries`**：超时是必要的——没有它，IG 挂了 / 连接僵死时 Host 会永远等 RECEIVED。但**重发次数上限不需要**——TCP 保证字节送达，超时的根因（IG 挂/连接断）重发无效，一次超时即失败即可。**第一版先用缺省值**：`sendCommand(msgId, payload, /*receivedTimeoutMs=*/1000)`，配置项入 JSON 留扩展位。

| API | 位置 | 说明 |
|-----|------|------|
| `sendCommand(cmd, payload, receivedTimeoutMs=1000)` | `HostSync` | 下发 + 等 RECEIVED（缺省 1000ms）；超时即失败 |
| `setCommandResultCallback(ack, seq, cmd)` | `HostSync` | 命令结果回调（RESULT 阶段） |
| `lastCommandResultSeq()/lastCommandResultAck()` | `HostSync` | RESULT 观测（测试） |

## 9. 验收要点

| 场景 | 断言要点 | 标签 |
|------|----------|------|
| 命令送达 + RECEIVED | Host 发 → IG 收到 → 回 RECEIVED → Host 判定送达 | `[acceptance][bdd][e2e]` |
| RESULT-ACK / NACK | IG 执行后回 RESULT → Host 回调成功/失败 | `[acceptance][bdd][e2e]` |
| Load → Place 顺序 | 先 LOAD 后 PLACE，按序执行 | `[acceptance][bdd][e2e]` |
| 指令生效（场景状态） | LOAD 真实加载 + PLACE 后，IG 场景持有该模型、实体位姿与 PLACE 设定一致 | `[acceptance][bdd][e2e]` |
| 指令生效（ECEF） | 配置驱动 coordFrame=Ellipsoid；LOAD+PLACE(pos=LLA) 后 IG 场景持有模型、位姿 = LLA 的 LocalToWorld 矩阵 | `[acceptance][bdd][e2e]` |
| RECEIVED 超时 | 超时未收 RECEIVED → 判定「未送达」（**注入 IG 延迟回 RECEIVED 复现**，非断线） | `[acceptance][bdd][e2e]` |
| IG 幂等去重 | 注入同 seq 重发 → IG 不重复执行（初版无同 seq 重发 API，IG 侧逻辑用注入验证） | `[unit]` |
| 长度分帧 | 粘包/拆包下 IGMsg 完整解析 | `[unit][wire-contract]` |
| 载荷内容 | `Msg` 携带 seq + payload，解析正确（CIGI V4 线格式：`[PacketSize][PacketID=0x0ff0][MsgID][reserved][Msg=seq+payload]`，Msg 8 对齐） | `[unit]` |
| 慢指令不误判 | 慢命令 RESULT 迟到，Host 不判失败（用真实 LOAD 慢命令复现：teapot 加载 ~数百 ms，3 帧 tick 内 RESULT 未到） | `[acceptance][bdd][e2e]` |
| 断线即失败 | IG 掉线 → `sendCommand` 等 RECEIVED 超时 → 返回 false（未送达） | `[acceptance][bdd][e2e]` |
