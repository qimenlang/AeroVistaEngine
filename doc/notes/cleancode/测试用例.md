# 测试用例知识总结

> 定位：记录软件测试各**层级**与**专项手段**的概念、原理与适用场景，作为知识索引。
> 与本仓库的关系：书写约定见 [测试用例书写规范](../测试用例书写规范.md)；AI+ATDD/TDD 实践见 [AI+TDD总结](AI+TDD总结.md)。本文是**通用知识总结**，重点放在最后两节（模糊测试、变异测试）。

---

## 0. 测试分层总览

测试按「测什么、问什么」分四层，常画成**测试金字塔**：越往下越贴近代码、数量越多、跑得越快；越往上越贴近真实交付、数量越少、越慢越贵。

| 层级 | 回答的问题 | 粒度 | 数量 / 速度 |
| ---- | ---------- | ---- | ----------- |
| **单元测试** | 这段实现算得对不对？ | 函数 / 类 / 算法 | 大量、最快 |
| **集成测试** | 模块拼起来接得对不对？ | 多模块接口 / 协议 / 数据流 | 中量、较快 |
| **系统测试** | 整机在目标环境里跑得怎样？ | 完整系统 + 真环境 | 少量、较慢 |
| **验收测试** | 该不该按约定收货？ | 需求 / 对外可观察行为 | 少量、慢（执行上常像系统测） |

> **形式 ≠ 层级**：用哪个框架（Catch2 的 `TEST_CASE` / `SCENARIO`、pytest、JUnit…）不决定层级；决定层级的是「测的是局部逻辑还是对外契约」。

模糊测试、变异测试**不属于金字塔的某一层**，它们是横切整个测试活动的**专项质量手段**：模糊测试针对「健壮性 / 安全」，变异测试针对「测试本身是否有效」。详见 §5、§6。

---

## 1. 单元测试（Unit Testing）

**概念**：针对最小可验证单元（一个函数、一个类、一个纯算法）做验证，输入确定 → 输出 / 状态变化可断言。

**原理 / 特点**：

- **隔离**：依赖的协作方用 mock / 桩（stub）替换，只测本单元，不受外部状态影响。
- **快**：无 I/O、无网络、无 GPU，毫秒级，适合频繁运行。
- **定位精准**：失败时直接指向出错的函数，debug 面最窄。

**典型例子**：矩阵分解、四元数归一化、AABB 合并、视锥裁剪判定、资源句柄引用计数、状态机迁移。

**与其它层级的关系**：数量最多的底座；但只能证明「零件对」，不能证明「零件拼起来对」——这正是集成测试的职责。

---

## 2. 集成测试（Integration Testing）

**概念**：把**多个真实模块**拼起来，验证它们之间的接口、协议、数据流是否正确衔接。

**原理 / 特点**：

- 关注**连接点**：调用约定、序列化格式、网络收发、共享状态传递是否正确。
- 边界外可真可假：外部系统（数据库、第三方服务）可 mock，但**被测系统内部的多个模块用真的**。
- 比单元慢、比系统快，失败时能缩小到「某两个模块之间接错了」。

**典型例子**：`SynchronSystem` 与本地 UDP / `MiniHost` 的收发联调；配置加载 → 引擎初始化 → 场景构建的链式调用。

**易混点**：把「mock 掉外部、只测本系统 I/O」有时叫**组件测试**，本质仍是带边界 mock 的集成；集成的核心是「连接是否正确」，不是「必须不 mock」。

---

## 3. 系统测试（System Testing）

**概念**：把**完整系统**部署到接近真实的环境里，验证端到端行为。

**原理 / 特点**：

- 用真资源：真 GPU、真文件、真网络、真实多进程 / 多线程。
- 验证**整体**而非局部：性能、资源占用、异常环境下的表现、跨模块的时序。
- 最接近真实，也最慢、最脆（受环境、时序、硬件差异影响大）。

**典型例子**：离屏 `Engine` 完整「加载模型 → 渲染一帧 → 截屏比对」；Host ↔ IG 多通道整链跑通。

> 注意：系统测试执行形态上和验收测试可以一样（都跑真 `Engine`），差别在**是否代表收货标准**——见下节。

---

## 4. 验收测试（Acceptance Testing）

**概念**：用**业务/产品语言**描述「怎样算做完、可收货」，把收货标准钉成可执行用例，回答「该不该按约定收货」。

**原理 / 特点**：

- 站在**使用者 / 业务**视角，写可观察结果，不写实现细节。
- 常与 **ATDD（验收测试驱动开发）**、**BDD（Given/When/Then）** 结合：先定 Done 再实现。
- **标准由产品 / 规格定**，不是开发自己拍板——这是与系统测试最本质的区别。

**典型例子**（Gherkin 风格）：

```gherkin
Scenario: 模型路径不存在时初始化失败
    Given 引擎以离屏模式启动
    When 加载不存在的模型 "models/missing.vsgt"
    Then 初始化返回失败
    And 不产生截屏文件
```

**区分三问**：① 失败时业务语言能否听懂？能 → 偏验收；② 是否一个完整对外故事？是 → 偏验收/系统；③ 是否必须串起多子系统/真环境？是 → 偏集成/系统，否则偏单元。

## 5. 模糊测试（Fuzzing）

### 5.1 概念

**自动化输入测试**：向程序喂入大量**随机、畸形、非预期的输入**，观察程序是否崩溃、卡死、内存泄漏或产生安全漏洞。名字来自「fuzz」——一堆杂乱无章的数据，像绒毛一样塞进程序。

它和人工测试是互补的：人工测「我想得到的边界」，模糊测试用机器去碰「没人想到过的输入」，以量取胜，专挖人工覆盖不到的深层缺陷。

### 5.2 原理

标准流程五个环节：

1. **种子（Seed）**：从一个或多个合法 / 半合法输入起步。种子质量决定效率——好种子让 fuzzer 更快触达深层代码路径。
2. **变异（Mutation）**：对种子随机改动（翻转比特、增删字节、拼接、替换字段），生成海量新输入。
3. **执行（Execution）**：把变异输入喂给被测程序（解析器、协议栈、编解码器、文件加载器等「吃外部数据」的代码）。
4. **监视（Monitor）**：观察反应——崩溃、断言失败、死循环、内存越界（配合 ASan / UBSan 等 sanitizer）、返回值异常。
5. **反馈（Feedback）**：现代 fuzzer 做**覆盖率引导**（coverage-guided）——记录哪些分支被新输入触发，只保留「能走进新路径」的输入作为新种子，不断深入，而非纯随机乱撞。

### 5.3 分类

| 维度 | 类型 | 说明 |
| ---- | ---- | ---- |
| 是否看程序结构 | **黑盒（Dumb）** | 不看代码，纯随机数据；简单但盲目，覆盖率低 |
| | **灰盒（Coverage-guided）** | 用插桩拿覆盖率反馈（AFL、libFuzzer），当前主流 |
| | **白盒（Smart）** | 分析源码 / 约束（如符号执行）定向生成；成本高、精度高 |
| 如何生成输入 | **变异型（Mutation-based）** | 改已有种子（AFL 为主） |
| | **生成型（Generation-based）** | 按格式语法直接生成，针对特定协议 / 文件格式 |

### 5.4 与 sanitizer 的配合

模糊测试通常**依赖 sanitizer** 放大观测能力：崩溃本身未必发生，但 ASan 能在越界读写、use-after-free 发生的第一时间报错。见 [Sanitizer 总结](Sanitizer.md)。可一句话记为：**fuzzer 负责生成烂输入，sanitizer 负责把"烂输入造成的隐患"变成"立刻可报的崩溃"。**

### 5.5 本工程适用点

攻击面最清晰的是**网络协议解析**——例如 CIGI 报文解析、`cigi_wire` 收包逻辑：把随机 / 畸形字节流塞给解析器，验证它不越界读、不崩、能优雅处理非法字段。资源加载入口（`.vsgt` / 模型 / 纹理）也是常见 fuzz 目标。

## 6. 变异测试（Mutation Testing）

### 6.1 概念

**「测测试」的手段**：故意把生产代码改坏（制造变异体），再跑现有测试套件，看测试能不能抓住这次改动。它**不找程序的 bug，而是评估测试用例本身是否有效**。

它和模糊测试连中文都带「变异」，但**变异对象完全不同**，容易混淆：

| | 模糊测试（Fuzzing） | 变异测试（Mutation Testing） |
| --- | --- | --- |
| 变异对象 | **输入数据** | **被测程序源代码** |
| 目的 | 找程序 bug（崩溃 / 越界 / 漏洞） | 评估测试用例的质量 |
| 回答的问题 | 「程序能扛住烂输入吗？」 | 「我的测试真的有用吗？」 |
| 产物 | 崩溃样本、漏洞报告 | 测试套件的「变异得分」 |

### 6.2 原理

1. **制造变异体（Mutant）**：对源码做微小改动，例如 `a + b` → `a - b`、`>` → `>=`、`if (x)` → `if (!x)`、删除一行语句。
2. **跑测试**：用现有测试套件跑这些「被动过手脚」的版本。
3. **判结果**：
   - 测试**挂**（发现代码被改）→ 变异体被**杀死（killed）**，说明测试对这个改动点敏感，是好的。
   - 测试**仍全绿**（没发现）→ 变异体**存活（survived）**，说明测试有**盲区**：改了这个地方都不会报错。
4. **变异得分（Mutation Score）** = 被杀死的变异体 / 总变异体。得分越高，测试套件越能捕捉逻辑错误。

### 6.3 核心价值

- 专治「**高覆盖率、弱断言**」：行覆盖 95% 看似漂亮，但如果断言只是「函数没抛异常」，改坏关键逻辑仍全绿，覆盖率就只是数字。
- 暴露「**测试与实现细节绑太紧**」的坏味道：绑定中间变量、mock 调用次数这类用例，往往在变异测试下存活率高。
- 与 ATDD 理念同源：**钉可观察结果，不钉实现细节**——正是变异测试下更不容易存活的写法。

### 6.4 与模糊测试的互补关系

一句话记忆：

- **模糊测试**：喂垃圾数据，看程序死不死（提升**健壮性**）。
- **变异测试**：故意把程序改坏，看你的测试能不能抓出来（提升**测试有效性**）。

一个在找程序的洞，一个在找测试的洞，两者互补，不互相替代。
