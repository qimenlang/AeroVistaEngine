# Socket 基础：TCP / UDP 与端口

多通道同步相关的通用网络知识。本项目具体选型见 [多通道同步模块设计.md](../design/多通道同步/多通道同步模块设计.md)。

---

## 1. UDP 不是“广播协议”

UDP 是无连接数据报，常用三种投递方式：

| 方式 | 含义 | 典型用途 |
|------|------|----------|
| **单播 unicast** | 发到某一个 `IP:port` | 点对点控制与回程（最常见） |
| **组播 multicast** | 一份数据，订阅者都收 | 一对多扇出优化 |
| **广播 broadcast** | 网段内尽量都收 | 少用（吵、受限） |

“用了 UDP”≠“在广播”。Host→多 IG 可以是 **单播扇出 N 次**，也可以是组播；默认单播更简单、更好控。

## 2. TCP 与 UDP 如何分工（一般原则）

| 流量特征 | 更合适 | 原因 |
|------|------|------|
| 周期性、时效优先、可丢（心跳、帧节奏、每帧状态） | **UDP** | 低延迟；丢了用下一帧补 |
| 必须落地执行（加载、切库、复位、业务指令） | **TCP** 或 UDP+序号/ACK/重传/幂等 | 需回执与重试 |

不建议把整条高频帧同步链路改成 TCP：队头阻塞与延迟抖动不利于显示同步。

TCP 与 UDP **端口号可以相同**（如 `8000/tcp` 与 `8000/udp`）：内核按协议区分，**不会在内核里互相阻塞**。真正要隔离的是应用收发路径（独立 socket / 独立循环），避免一边阻塞读拖死另一边。

### 2.1 仿真里常说的「加载 / 切库 / 复位」（TCP 命令面）

多通道 / IG 语境下，这三类通常指 **Host 通过可靠通道让各 IG 改变场景状态** 的指令（本仓库命令面已落地实体摆放/文本指令，见 §2.1 命令面载荷与链路选择；**加载 / 切库 / 复位指令本身尚未实现**）：

| 词 | 含义（直观） | 典型目的 |
|----|--------------|----------|
| **加载** | 让 IG **打开/装入**某个场景或模型资源（如指定 `.vsgt` / 数据库） | 各通道显示同一套（或约定好的）内容后，再开始跟拍 |
| **切库** | **切换**当前使用的场景库 / 地形库 / 模型库（从 A 套内容换成 B 套） | 任务中途换区域或换场景，多通道要一起切，避免有的窗还是旧库 |
| **复位** | 把 IG 侧状态 **恢复到约定初始**（清临时状态、回到默认视点/默认场景等，具体范围由协议定义） | 出错或一场结束后续跑，各通道回到同一起点 |

为何倾向走 **TCP（或 UDP+ACK）**：这类指令「执行与否」必须有答案；失败要能重试。常配 **ACK/NACK**（成功/失败回执）和序号，避免重复执行（幂等）。  
与 **UDP 同步面**（每帧 IGCtrl/SOF）分开：帧同步可丢，加载/切库/复位不能 silently 丢。

**命令面载荷与链路选择**：所有 CIGI 报文在 TCP/UDP 都支持发送，按语义选链路——**持续周期性下发（实时控制位姿）走 UDP（无回执，丢包自愈）；一次性精准送达（摆放位姿、指令）走 TCP（传输层可靠，无业务回执）**。命令帧在 TCP 上承载多种报文：`CigiEntityPositionCtrlV4`（摆放位姿，`0x01` 定长 48B）、`CigiSymbolTextDefV4`（文本指令，`Text` 空格分隔、`std::string` 变长）。**均 fire-and-forget、无应用层 ACK/NACK**。TCP 字节流需按 CIGI 包头 `PacketID + PacketSize` 长度分帧。详见 [状态同步设计初版.md](../design/多通道同步/状态同步设计初版.md) §4。

## 3. 本地端口 vs 发送目标

| 概念 | 含义 |
|------|------|
| **本地 bind 端口** | 本机 `bind`，用来收包 |
| **发送目标** | `sendto(对方IP, 对方端口)` 或 TCP `connect` 的对端 |

收发“端口分离”指的是 **本端收口与对端收口可以是不同端口号**，并不意味着发送方要为每个对端再 `bind` 一个本地发送端口。  
一个 UDP socket 通常：`bind` 一个本地收端口 + 向多个远程 `IP:port` 做 `sendto`。

TCP 服务端：`listen` **一个**端口，`accept` 出 **N 条连接**；不是 N 个 listen。

### 3.1 bind 地址：0.0.0.0 与 127.0.0.1

`bind` 时选的「地址」决定 **本机这个 socket 收哪些网卡的包**，与「发往对端」无关。

| 地址 | 含义 | bind 后能收到谁的连接 |
|------|------|----------------------|
| `127.0.0.1` | **回环 loopback**：数据不出网卡，只在 OS 内部转一圈 | 只有本机用 `127.0.0.1`/`localhost` 访问；局域网其他机器连不上 |
| `0.0.0.0` | **`INADDR_ANY` 通配**：绑定所有网卡，不是真实 IP | 任何接口进来的包都收（本机回环 + 局域网 IP），局域网机器可连 |

- 服务器对外监听 → bind `0.0.0.0`；只准本机连 → bind `127.0.0.1`。
- 客户端**连接目标**不能用 `0.0.0.0`：本机服务用 `127.0.0.1`，跨机器用对端局域网 IP。
- 本项目：Host/IG 本地 UDP 接收、Host TCP 监听**固定 `0.0.0.0`（INADDR_ANY）**；`bindAddr` 配置已移除（从未被消费）。IG 跨机器连 Host 靠 `igConfig.targetAddr` 填 Host 局域网 IP，见 [sync模块化设计.md](../design/多通道同步/sync模块化设计.md) §4.0。

## 4. UDP 单端口双向 vs 双端口交叉

| 方案 | 做法 | 优势 | 劣势 |
|------|------|------|------|
| 单端口双向 | 双方都用同一端口号收发（不同机器 IP 不同） | 端口少、配置简单 | **同机**同时起两端易 bind 冲突；抓包难靠端口区分上下行 |
| 双端口交叉 | A 发→P0 / 收←P1，B 发→P1 / 收←P0 | 同机联调友好；端口可区分方向 | 每链路两个角色端口，配置易配反 |

同机 Host+IG 联调、希望按端口区分上下行时，双端口交叉更合适；纯多机部署时单端口也常见。

## 5. “已连接”怎么检查

| 平面 | 仅 socket 就绪（不够） | 建议的连通判据 |
|------|------------------------|----------------|
| **UDP** | `bind` / 能 `sendto` 成功 | 收到对端预期报文（或探测+应答）并在超时内完成 |
| **TCP** | `socket` 创建成功 | `connect`/`accept` 成功；可选应用层握手 ACK |

UDP **没有** TCP 那种握手连接；不能把 `bind` 成功当成“已连上对端”。  
分项状态（如 `udpSynced` / `tcpConnected`）应分开检查，便于判断是哪一平面失败。

客户端连服务端时，**UDP `sendto` 与 TCP `connect` 都需要对方 IP**（或可解析的主机名）。服务端 TCP `listen` 可先不写死客户端 IP；若服务端还要对客户端做 UDP 单播，仍需客户端地址表（配置或接入时上报）。

### 5.1 TCP 断开检测：EOF 与物理断网

**EOF（End of File）不是对端「主动发来的消息」，而是本地 `recv` 返回 `0` 的检测结果**——表示对端已关闭发送方向（TCP 栈已收到并处理了对端的 `FIN`/`RST`）。

```text
recv(sock, buf, len)
  → 返回 > 0 ：读到数据
  → 返回 0   ：对端关闭写方向（EOF）→ 之后永远读到 0
  → 返回 < 0 ：出错（如连接被 RST 重置）
```

| 对端发生的事 | 本地 `recv` 观察到 |
| --- | --- |
| **对端正常退出 / 调 close** | 对端 TCP 栈自动发 `FIN` → 本地 `recv` 返回 **0（EOF）** |
| **对端崩溃 / 被杀** | OS 清理 socket，发 `FIN`（优雅）或 `RST`（异常）→ `recv` 返回 **0 或错误** |
| **对端物理断网 / 网线拔了** | 收不到 `FIN`/`RST`，本地 `recv` **卡住**（等 TCP 超时）→ **不会立即 EOF** |

**关键**：EOF 是 **TCP 协议层的机制**（FIN 握手的结果），不是应用层报文——对端不会「主动发一个 EOF 包」；本地方检测到「连接结束」。

**优雅断开 vs 物理断网（两种检测路径）**：

| 场景 | 检测方式 |
| --- | --- |
| **优雅断开**（FIN/RST 到达） | `recv` 返回 0 → 立即判定断开 |
| **物理断网**（无 FIN/RST） | `recv` 卡住 → 需 **`recv` 超时**（`SO_RCVTIMEO`）或**应用层心跳/保活**兜底，超时未收到数据才判定断开 |

所以「读循环接管断线检测」的完整判据是：**`recv` 返回 0 = 优雅断开；`recv` 超时无数据 = 疑似物理断网（需超时阈值/心跳确认）**。单靠 EOF 检测覆盖不了「网线拔了」这类无 FIN/RST 的场景。

## 6. 主从连接语义（常见）

| 角色 | 典型行为 |
|------|----------|
| 服务端（如 Host） | 初始化：bind / listen，**等待**客户端 |
| 客户端（如 IG） | 初始化：本地 bind，再 **Connect** 到服务端 |

服务端一般不主动 `Connect` 客户端；“全部就绪”由服务端汇总 N 个客户端状态。

## 7. Peer（对等端）是什么

**Peer** = 通信里的「对面那一端」。对 Host 来说，每一个连上来的 IG 就是一个 peer。

| 概念 | 含义 |
|------|------|
| **Peer** | 一个对端实体（本项目里通常是一台/一个进程上的 IgSync） |
| **Peer 表** | Host 侧维护的「当前有哪些 IG、怎么联系、是否就绪」的名单 |

Host 要向多 IG **单播扇出**时，必须知道每个 IG 的 `IP` + `udpRecvPort`，以及 TCP/UDP 是否都握手完成；这些信息就记在 peer 表里。  
本项目实现：`HostSync` 内 `IgPeer{clientId, ip, udpRecvPort, tcp, tcpReady, udpReady}`；两端 ready 才计入 `readyIgCount` 并参与 IGCtrl 扇出。详见 [多通道同步模块设计.md](../design/多通道同步/多通道同步模块设计.md) §2.3。
