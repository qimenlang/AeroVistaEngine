# Code Metrics（代码质量指标）

**Code Metrics(代码度量)**是用一组**可计算的数值**描述代码的结构与规模，用来辅助判断代码难不难改、测不测的动、有没有失控，不直接证明功能正确性；

## 1.解决的问题

人眼看代码只能定性：这段代码好乱。code metrics 把部分质量编程：

- **可设门槛**（圈复杂度>15禁止合入）
- **可比较**（模块A比模块B复杂）
- **可跟踪**（迭代后复杂度升还是降）

对AI辅助开发，检测代码质量、架构变动尤其有用；

## 2.原理（共性）

code metrics都遵循的流程：

```txt
源码 / AST / 控制流图 / 依赖图
        ↓  按定义计数或公式
     标量或分布（如每个函数一个值）
        ↓  与阈值 / 历史对比
     告警、报表、质量门禁
```

- **输入**：语法结构、依赖关系、体量
- **输出**：标量、分布等数值
- **假设**：结构越缠、体量越大、耦合越乱 -> 维护与测试成本越高，缺陷风险越大

## 3.度量内容

#### 3.1规模

| 指标             | 含义                | 典型用途                   |
| :--------------- | :------------------ | :------------------------- |
| LOC / SLOC       | 物理行 / 有效代码行 | 体量、趋势                 |
| 注释率           | 注释与代码比        | 过低或缺文档信号（易被刷） |
| 文件/类/函数数量 | 模块切分粒度        | 是否碎裂或巨石             |

#### 3.2复杂度

1. ##### **圈复杂度 Cyclomatic  Complexity**

   - 在函数的**控制流图（CFG）**上：V(G)=E−N+2 
     - V(G) ：控制流图上的**独立路径数**
     - N ：节点（基本块），E：边 ，2：输入输出
   - 直观 ：独立路径条数：`if/else/case/&&/||/循环` ；
   - 作用：提示单测要覆盖多少路径；过高则建议拆分
   - 经验门槛（自定）：单函数<=15 （常见）
   - **符号概念**

   | 符号   | 含义                         |
   | ------ | ---------------------------- |
   | \(N\)  | 节点数（基本块）             |
   | \(E\)  | 边数（可能的执行走向）       |
   | \(+2\) | 单入口单出口连通图的常用修正 |

2. ##### 认知复杂度 Cognitive Complexity

   - 更贴近认读起来费不费劲（嵌套、断续的逻辑，计分时惩罚更大）

     - 人读代码时，线性顺序是否被打破，尽量少嵌套结构
     - 使用Sonar规则；
   - 比圈复杂度更适合做[可读性]门禁，
   - Sonar 规则:

     - 结构增量：if else 等，通常+1;
     - 嵌套增量：当前深度为d时，遇到上述结构，按深度+d;
     - 短路径逻辑：一行里多个 逻辑运算符，按条件数加点；

   | 概念             | 精炼                                                         |
   | ---------------- | ------------------------------------------------------------ |
   | **断续**         | 线性阅读被打断：中途 `return` / `break` / `continue` 等，要跳走再接上 |
   | **惩罚**         | 计分时**额外加分**：嵌套越深，内层分支加点越多；断续结构再加点 |
   | **量化（直觉）** | 分支/循环等 +1；按嵌套深度再加；断续 +1；多条件 `&&/\|\|` 按个数加点（以 Sonar 规则为准） |

#### 3.3面向对象/设计结构

| 指标方向 | 含义                     |
| :------- | :----------------------- |
| 耦合     | 依赖别人多少             |
| 内聚     | 成员是否各干各的         |
| 继承深度 | 继承链是否过深           |
| 响应集   | 一个类可能响应的方法规模 |

C++ 引擎代码里更常看：头文件依赖、模块扇出、循环依赖，不一定套完整 CK 套件。

#### 3.4依赖与架构

- 依赖方向：上层依赖下层，不能颠倒
- 循环依赖：A<->B
- 不稳定度/抽象度：设计是否是**稳定的抽象**
- 常用工具：自定义 arch unit、clang-tidy、Include-What-You-Use、依赖图脚本等；

#### 3.5重复与味道

- 重复代码比例
- 过长的参数列表、过大类、过深嵌套

## 4.作用

- 定位难维护热点：高复杂度+高变更频率 = 优先重构；
- 设质量闸门：CI失败于新增超复杂函数；
- 约束AI产出：绿测仍可能结构崩；
- 趋势管理：禁止复杂度只升不降；
- 辅助测试投入：复杂度高的模块，多增加单测、验收；

## 5.实践

```txt
工具扫描（clang-tidy / Sonar / 脚本）
  → 报表（按文件/函数）
  → 门禁（仅增量或核心目录）
  → 人审（热点才重构，不为指标而指标）
```

实践建议：

- 少量硬阈值（如关键路径圈复杂度、禁止新循环依赖），优于几十个模糊分；
- 对新增、改动代码设门禁，比全仓库立刻达标 可行；
  - CI/pre-commit/分析工具中，只扫描本次diff涉及的文件、函数；
  - 历史旧环可冻结后逐步拆，最终追求无循环依赖；
- 使用工具

| 工具                       | 主要给什么                             |
| :------------------------- | :------------------------------------- |
| lizard                     | 圈复杂度（CCN）+ 规模                  |
| Sonar                      | 认知复杂度，支持全部语言，需要网络接口 |
| clang-tidy cognitive check | 认知复杂度，本地检测                   |

lizard 参数：

| 指标   | 全称/含义                    | 直观理解                                                     |
| :----- | :--------------------------- | :----------------------------------------------------------- |
| NLOC   | Non-comment Lines Of Code    | 函数里「有效代码行」数（大致不含空行/纯注释行）              |
| CCN    | Cyclomatic Complexity Number | 圈复杂度：独立路径大概有多少条。`if/else/for/while/&&/||/case/?` 等会抬高它 |
| token  | Token count                  | 词法单元数量（标识符、运算符、括号等），越大通常代码越「密」 |
| PARAM  | Parameter count              | 形参个数                                                     |
| length | Function length              | 从函数开头到结尾占的行跨度（含空行/注释时往往 ≥ NLOC）       |
| ND     | Nesting Depth                | 最大嵌套深度（lizards 扩展；这里都是 0，可能未启用该扩展或该版未算） |

## 6. 本仓库：圈复杂度与认知复杂度配置

策略一句话：**增量门禁**——pre-commit / CI 只检查本次涉及的文件，超标失败；本地可增量编译反馈（认知）或脚本全量自查。两种指标算法不同，阈值数字接近不代表等价。

### 6.1 指标与阈值

| 指标             | 工具                                                   | 阈值                  | 配置位置                                             |
| ---------------- | ------------------------------------------------------ | --------------------- | ---------------------------------------------------- |
| **认知复杂度**   | clang-tidy `readability-function-cognitive-complexity` | **20**（可再收到 15） | 仓库根 `.clang-tidy` → `CheckOptions`                |
| **圈复杂度 CCN** | lizard（`-C` / `--ccn`）                               | **15**                | `scripts/lizard_engine.py` 默认；CI/手工可传 `--ccn` |

门禁失败方式：

- 认知：`scripts/clang_tidy_engine.py` 使用  
  `-warnings-as-errors=readability-identifier-naming,readability-function-cognitive-complexity`  
  （`.clang-tidy` 里 `WarningsAsErrors` 为空，真正升 error 靠脚本参数）
- 圈复杂度：lizard `-w`，有告警则非 0 退出（可用 `--ignore-warnings -1` 只报不失败，门禁路径不用）

lizard 告警字段速查：`NLOC` 有效行、`CCN` 圈复杂度、`token` 词法单元、`PARAM` 参数个数、`length` 函数行跨度、`ND` 嵌套深度（未开扩展时常为 0）。

### 6.2 扫描范围

|       | 认知复杂度 (clang-tidy)                                      | 圈复杂度 (lizard)                                |
| ----- | ------------------------------------------------------------ | ------------------------------------------------ |
| 包含  | `engine/**` 源/头（经脚本映射到 `.cpp` TU）                  | `engine/source/**/*.cpp`                         |
| 排除  | `thirdparty/`；**Tests 关掉认知** | `engine/Tests`（脚本根目录即为 `engine/source`） |
| Tests | `engine/Tests/.clang-tidy`：`InheritParentConfig` + `-readability-function-cognitive-complexity`（Catch2 宏膨胀） | 不扫                                             |

命名检查 `readability-identifier-naming` 与认知共用 `.clang-tidy` / tidy 脚本；Tests 仍保留命名规则。

### 6.3 相关文件一览

| 路径                               | 作用                                                       |
| ---------------------------------- | ---------------------------------------------------------- |
| `.clang-tidy`                      | 启用 naming + 认知复杂度；阈值 20                          |
| `engine/Tests/.clang-tidy`         | 测试目录关闭认知检查                                       |
| `engine/CMakeLists.txt`            | 本地设 `CMAKE_CXX_CLANG_TIDY`；**`GITHUB_ACTIONS` 下跳过** |
| `scripts/clang_tidy_engine.py`     | 跑 clang-tidy；pre-commit / CI 共用                        |
| `scripts/lizard_engine.py`         | 跑 lizard CCN；pre-commit / CI 共用                        |
| `scripts/ci_changed_complexity.py` | CI：对 `base...HEAD` 改动文件依次调上述两脚本              |
| `.pre-commit-config.yaml`          | local hooks：`clang-tidy`、`lizard`                        |
| `.github/workflows/build&test.yml` | `ci-debug`：Complexity gates（diff + 失败即红）            |

### 6.4 本地

**依赖**

```text
pip install pre-commit lizard
pre-commit install
# clang-tidy 在 PATH；并已配置出 compile_commands.json，例如：
cmake --preset clang-Ninja
# 可选：AEROVISTA_TIDY_BUILD_DIR=<含 compile_commands.json 的构建目录>
```

**认知复杂度**

| 方式       | 行为                                                         |
| ---------- | ------------------------------------------------------------ |
| 本地编译   | `engine/CMakeLists.txt` 设置 `CMAKE_CXX_CLANG_TIDY`：增量构建只对**重编的 TU**跑 tidy（含认知）。默认**不**把 tidy warning 当编译失败（升 error 在脚本的 `-warnings-as-errors`）。改阈值后需重编对应 `.cpp` 才会再跑。 |
| 脚本       | `python scripts/clang_tidy_engine.py [文件…]` 或 `--all-engine` |
| pre-commit | 暂存且匹配 `engine/*.{cpp,h,…}` 的文件       |

**圈复杂度**

| 方式       | 行为                                                         |
| ---------- | ------------------------------------------------------------ |
| 本地编译   | **不**挂 CMake（避免全量 post-build 与「只查改动」冲突）     |
| 脚本       | `python scripts/lizard_engine.py [文件…]` 或 `--all-source --ccn 15` |
| pre-commit | 暂存且匹配 `engine/source/*.{cpp,…}` 的文件；超标失败        |

**不在 CMake 里对 lizard 加编译后自动命令**：全量扫与增量门禁策略不一致；本地圈复杂度以 pre-commit / 脚本为准。

### 6.5 pre-commit

安装：`pip install pre-commit lizard && pre-commit install`。

| Hook id      | entry                                 | 文件过滤                                 | 失败策略                 |
| ------------ | ------------------------------------- | ---------------------------------------- | ------------------------ |
| `clang-tidy` | `python scripts/clang_tidy_engine.py` | `^engine/.*\.(cpp\|h\|…)$` | naming / 认知超标 → 失败 |
| `lizard`     | `python scripts/lizard_engine.py`     | `^engine/source/.*\.(cpp\|…)$`           | CCN>15 → 失败            |

只处理 hook 传入的改动文件，不做全库扫描。

### 6.6 CI（GitHub Actions）

工作流：`.github/workflows/build&test.yml`，在 **`ci-debug`** 矩阵任务中：

1. `checkout` 使用 `fetch-depth: 0`（便于算 diff）
2. 构建阶段：**不**启用 `CMAKE_CXX_CLANG_TIDY`（`GITHUB_ACTIONS` 已跳过），避免 clean build 对全库跑 tidy
3. 步骤 **Complexity gates**：`pip install lizard` 后执行  
   `python scripts/ci_changed_complexity.py --build-dir out/build/ci-debug --ccn 15`
4. diff 基准：PR 用 `GITHUB_BASE_SHA`（base commit）；push 用 `GITHUB_EVENT_BEFORE`；否则 `HEAD~1`
5. 过滤后分别调用 `clang_tidy_engine.py` / `lizard_engine.py`；**任一门禁失败则 CI 失败**
6. 本次 diff 无匹配引擎文件 → 跳过对应工具并成功

与 pre-commit 同一增量策略；**不对全库 `--all-engine` / `--all-source` 做阻断**（全量仅供本地自查）。

### 6.7 为何 CI 构建跳过 `CMAKE_CXX_CLANG_TIDY`

- CI 是干净全量编译，挂 tidy 会对**每个** engine TU 再跑一遍认知检查，与「只查 diff」冲突，且拖慢、刷屏
- 正式门禁已由 `ci_changed_complexity.py` 承担
- 本地保留该变量：增量编译 ≈ 只检查重编文件，便于开发期反馈

### 6.8 常用命令

```bash
# 认知：全量 / 指定文件（需 compile_commands.json）
python scripts/clang_tidy_engine.py --all-engine
python scripts/clang_tidy_engine.py engine/source/function/sync/IgSync.cpp

# 圈复杂度：全量 / 指定文件
python scripts/lizard_engine.py --all-source --ccn 15
python -m lizard engine/source -C 15 -w

# 模拟 CI 增量门禁（相对某 base）
python scripts/ci_changed_complexity.py --base origin/develop --build-dir out/build/clang-Ninja --ccn 15

# 只跑某个 pre-commit hook
pre-commit run clang-tidy --files engine/source/function/sync/IgSync.cpp
pre-commit run lizard --files engine/source/function/sync/IgSync.cpp
```

### 6.9 演进与注意

- 阈值：认知可先 20 再收到 15；CCN 默认 15。两数同量级是工程习惯，**不是同一公式**
- 碰触存量超标函数所在文件时，增量门禁会失败——应顺手拆分或暂时不扩大该函数复杂度
- 仅改 `.clang-tidy` 阈值不会触发增量重编；需 touch/重编对应源文件，或直接跑脚本
- 未接 Sonar；圈复杂度不强制上 Sonar，lizard 足够做 CCN 门禁
