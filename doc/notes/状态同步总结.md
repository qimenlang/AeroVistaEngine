# 状态同步知识总结

多通道同步中「状态内容」与 CIGI **Message Synchronization（报文节拍）** 的知识。本项目状态/节拍**设计**见 [状态同步设计.md](../design/多通道同步/状态同步设计.md)。Present 对齐见 [帧同步总结.md](./帧同步总结.md) / [帧同步设计.md](../design/多通道同步/帧同步设计.md)。仿真时间消费见 [时钟同步总结.md](./时钟同步总结.md) / [时钟同步方案.md](../design/多通道同步/时钟同步方案.md)。开发前基线测量见 [多通道同步验收测量设计.md](../design/多通道同步/多通道同步验收测量设计.md)。四层总览见 [多通道同步业务梳理.md](./多通道同步业务梳理.md)。报文名录见 [cigi梳理.md](./cigi梳理.md)。

权威原文：SISO-STD-013-2014（CIGI 4.0）§4.2 Message Synchronization。下文 §3 / §4 为该两小节的对照翻译；§5 解释 `Ln`（latency）/ creeping / jitter。术语按 ICD 原样（Host、IG、IG Control、Start of Frame / SOF、Timestamp、VSync）。

---

## 1. 在四层里管什么

```text
时钟同步：大家手表一致            （时间基准）
状态同步：大家算同一个世界        （数据内容）
帧同步：  大家同时 Present 同一帧 （应用换帧时刻）
显示同步：显示器扫描相位一致      （物理扫描时序）
```

- **状态同步**：眼点、实体、环境等权威内容——包**里**是什么。
- **Message Synchronization（ICD §4.2）**：这些包按什么**节奏**在 Host↔IG 之间走——谁决定何时发下一包。不是 Present 栅栏（CIGI **没有** Present Barrier 包）。
- 命令/控制面（加载、摆放）可归入状态同步的宽泛范畴，工程上常与高频 UDP 数据面拆开（本项目 TCP 命令面，见 [状态同步设计.md](../design/多通道同步/状态同步设计.md)）。

---

## 2. ICD §4.2 标题在管什么

| ICD | 管什么 |
| --- | --- |
| **§4.2.1 Asynchronous** | Host 按自己的间隔发 IGCtrl；IG 自持帧率；建议用 Timestamp 纠延迟 |
| **§4.2.2 Synchronous** | IG 的 SOF（常挂这台 IG 的 VSync）卡住 Host；每帧一对报文 |
| **§4.3 帧号** | 丢包检测；Host Frame Number 与 IG Frame Number **独立**（CIGI 3.2 起） |

SOF 典型含义是「我这一显示帧**开始了**」（heartbeat），不是「第 N 帧已渲完、可以一起 Present」。

ICD 默认一对 Host–IG。多 IG 时工业上只认一台 **master** 的 IG→Host 心跳，再把同一份 Host 状态扇出全体——那是「共用一份状态」，不是各 IG 等齐上屏。

---

## 3. §4.2.1 Asynchronous Operation（对照翻译）

异步模式下，**Host 可以按任意间隔向 IG 发数据**。报文可以由 Host 内部的系统定时器或其他事件触发。IG 也可以向 Host 回送状态和任务功能数据；但 **Host→IG 的间隔由 Host 自己决定**。

与此同时，IG 应保持稳定帧率。每一帧，IG 应检查接收缓冲里有没有 CIGI 报文，并按收到的内容更新内部状态。

因为 Host 可能在 IG **某一帧的任意时刻** 发来报文，位置及其他状态变化往往要等到 **下一帧开头** 才被应用。这会引入最多接近 **一整帧** 的额外延迟（ICD Figure 2 的 `Ln`）。

IG 在 `tn` 开始第 n 帧。该帧进行中某时刻收到 Host 报文。但 IG **已经查过入站数据**，这条报文要等到下一帧开始 `tn+1` 才真正被读。此时报文里的数据已经过时了 `Ln`，最早也要到 `tn+2` 才会画进画面，总延迟约为 **`Ln + Tn+1`**。

`Ln+1` 往往比 `Ln` 更大。Host 与 IG 帧率不完全相等时，帧偏移会 **creep（爬移）**。爬移方向不同，IG 某一帧就经常收到 **0 条或 2 条** Host→IG 报文，造成 **frame jitter**（用语见 §5）。

为减轻滞后和抖动，IG 可以每帧外推位置。IG Control 与 Start of Frame（ICD §6.1.1、§6.2.1）里有 **Timestamp**：相对某个初始参考时刻已经过了多久。IG 可根据前几帧或 Velocity / Acceleration Control（§6.1.8、§6.1.20）估算当前帧实体位置。

实体往往变化很快，外推容易出错。因此异步模式 **只建议用于低保真**，或在无法同步运行时配合 **共享时基（Shared Time Base）**。

## 4. §4.2.2 Synchronous Operation（对照翻译）

同步模式下，**IG 必须向 Host 发一条 IG→Host 报文，表示新的一帧开始**。这条报文通常由显示系统的 **VSync** 驱动，当作规定双方何时交换数据的 **heartbeat**。报文里还可以带任务功能应答、事件通知及其他 IG 数据。

Host **必须立刻**用自己的报文回应：上一帧场景变化的实体位置/姿态、部件状态等。然后 Host 开始下一轮计算；IG 则更新并渲染场景。

这样 Host 数据在 **每一 IG 帧开头就已就绪**，消掉 Figure 2 里的额外延迟 `Ln`。Host 帧率由 IG 约束，也能减轻帧不对齐造成的 creeping / jitter（§5）。

ICD Figure 3：IG 发 SOF（常挂 VSync）→ Host 立刻回 IG Control（上一帧数据）→ IG 用这份数据更新场景图并渲染。

受带宽和传输延迟影响，IG 可能来不及在下一帧开始前收完应答并渲完。可以引入 **时间偏移**（Figure 4）：IG 在下一帧真正开始 **稍早一点** 就发 IG→Host 报文，让 Host 数据在 IG 整帧计算/渲染时间内到达。传输延迟帧间会变，偏移可按 **最坏网络负载** 调。

## 5. `Ln`、creeping、jitter（ICD 用语）

都出自 §4.2.1 Figure 2。前提：IG **每帧开头查一次**缓冲（本项目 `preFrame` / `drainIncoming`），之后到的包要等下一帧；Host 按自己的钟发，不等 IG。不是 GPU 卡顿，也不是屏幕撕裂。

### 5.1 `Ln` — **latency**（第 n 帧入站延迟）

ICD 图上的符号就是 **latency** `Ln`：包已到达、但错过本帧查缓冲，要等到 `tn+1` 才读；数据先过时了 `Ln`（最多近一帧 `Tn`）。上屏还要再加本帧更新+渲染，总滞后约 `Ln + Tn+1`。这是取样相位，不是网卡 RTT（60Hz 约 0～16ms）。

| | |
| --- | --- |
| **原理** | 包落在「查缓冲」之后 → 本帧不用。 |
| **现象** | 眼点/实体慢一拍（noticeable lag）。 |
| **原因** | 异步：Host 可在 IG 帧内任意时刻到达。 |
| **解决** | §4.2.2：SOF 把门，让 IGCtrl 赶在该 IG **帧头**就位。治标：Timestamp 外推。 |

### 5.2 creeping — **frame-offset creeping**（帧偏移爬移）

`Th`、`Ti` 是 **周期**（相邻两次发 IGCtrl / 相邻两次 IG 查缓冲的间隔），不是 fps。`fps = 1 / 周期`。

```text
Host 60fps → Th ≈ 16.7ms      IG 60fps → Ti ≈ 16.7ms
Host 50fps → Th = 20ms        Host 120fps → Th ≈ 8.3ms
```

Creeping：两边 **独立走钟且周期对不齐** 时，包落在 IG 帧里的位置每帧挪一点，`Ln` 跟着变。都标 60fps 也会爬（VSync 16.67ms vs `SetTimer(16)`）。

ICD 的「某帧 0 包、邻帧 2 包」特指 **两帧率接近、平均约 1 包/IG 帧** 时的回绕。

| 帧率 | 每 IG 帧大概几包 | 还会 creeping？ | 会不会空帧 |
| --- | --- | --- | --- |
| Host 50、IG 60 | 平均 ≈ 0.83 | 会 | **会**（有的 IG 帧 0 包） |
| Host ≈60、IG 60 | 大多 1 | 会（慢爬） | 偶发 0 或 2 |
| Host 120、IG 60 | 平均 2 | 落点仍会爬（两钟未锁） | **一般不会 0 包**；对不齐时偶发 1 或 3 |

**50 vs 60**：就是 ICD 那种空帧 creeping。**120 vs 60**：通常每帧都有包，空帧基本没有；但两包落在帧前半还是后半仍在漂（`Ln` 仍变），除非 Host 被 SOF 锁成严格 2:1。

| | |
| --- | --- |
| **原理** | 包相对 IG 查缓冲点的相位按 `Th − Ti` 每帧挪一截。 |
| **现象** | 近帧率：`Ln` 渐变，回绕时 0/2 包。倍频：每帧多包，空帧少见。 |
| **原因** | 帧钟未锁。 |
| **解决** | SofGated：Host 跟 master SOF，周期被拉成同一拍。只消那台 master；其它 IG 未锁 VSync 仍会爬。 |

```text
近帧率（ICD）：   ^  *     ^   *      ^ *        ^*  *   ← 回绕：0 包然后 2 包
Host 约 2× IG：  ^ * *   ^  * *    ^ *  *     ← 几乎总有包，落点仍在爬
```

### 5.3 frame jitter — **frame jitter**（帧抖动）

这里的 jitter = Host 状态在 IG 时间轴上 **时而 0 样本、时而 2 样本**，不是渲染耗时忽长忽短。

| | |
| --- | --- |
| **原理** | creeping 回绕 → 步进停一拍或连跳两拍。 |
| **现象** | 运动发顿、轨迹不匀。本项目：0 包复用末次眼点；2 包同一 `preFrame` 回调两次，画面留最后一次。 |
| **原因** | 近帧率 creeping 的 0/2 交替（Host 快很多倍是持续多包，另说）。 |
| **解决** | 先消 creeping（同步节拍）。辅以 Timestamp 外推抹空帧。高保真不要纯异步。 |

`Ln` / creeping / jitter 不是网络 RTT、不是撕裂、不是 GPU busy。SOF heartbeat 只门控「何时发下一包」，不是 Present 栅栏。

## 6. 与 §4.2 配套的帧号（ICD §4.3，摘要）

同步模式下用顺序帧号检测丢包。**Host Frame Number** 与 **IG Frame Number** 各自独立：对方在下一包里回显「Last Host / Last IG Frame Number」。这是送达确认，不是 Present 钥匙。

异步模式下不应把该机制当成「某一条指定报文已送达」的校验，但仍可用来观察对端是否在处理报文。

## 7. 讨论沉淀（知识结论）

下列不是 ICD 原文，是对照本项目读标准之后的结论。工程开关与时序落点见 [状态同步设计.md](../design/多通道同步/状态同步设计.md) §3。

### 7.1 异步：Host 与 IG 帧率不同

- **Host 明显快于 IG**：IG 一帧 `drainIncoming` 可能积压多条同类型 `IGCtrl` / 眼点（持续过采样，不是 §5.2 那种近帧率 creeping 的偶发 0/2）。本系统订阅是 **来一条回调一次**，没有「同 PacketID 只留最后」。画面写相机仍是该帧 `update` 里一次 `applyLastHostEye`（末次 compose 生效）；中间 compose 与多条 SOF 回显是重复劳动。命令面 **不能** 在 drain 里 squashing 同类型。
- **Host 慢于 IG**：某 IG 帧 0 条 Host 包（creeping 或持续欠采样）。IG **不会卡死**：相机复用末次合成位姿，`simTimeUs` 短窗口外推后冻结。观感是跟拍变台阶，不是引擎停住。ICD 说高保真别单靠异步，**不是**「Host 一旦慢于 IG 就不能用 FreeRun」。
- 两帧率**接近但不齐**时的 `Ln` 爬移、0/2 包与 jitter，见 §5。

### 7.2 同步：SOF→IGCtrl 时延量级

未在本仓库实测。局域网量级：loopback 约 0.05–0.2ms；千兆同交换机单程约 0.1–0.5ms（调度可到 1–2ms）；Host 组包 + 约 10 台 `sendto` 约 0.1–1ms。一次 **SOF → Host → 全体 IGCtrl 送达** 顺时大约 **0.5–3ms**。相对 60Hz（约 16.7ms）算短，但 ICD 仍写了 Figure 4，因为可能赶不上「下一帧开头前渲完」。

### 7.3 SOF 相位：帧头才能本帧生效

- SOF 放在 **帧头**（或上一帧 Present / VBlank，即 Figure 4）：包若在本次 `preFrame` 结束前入队，**同一次 `render` 就能用**。
- 多 IG：master 的 VBlank ≠ 全体 IG 的 VBlank。普通 IG 若已经走过自己的 `preFrame`，同一份 `IGCtrl(N)` 会落到它的下一圈。这是相位差，不是「drain 了还强制再等一帧」。

SOF 再快也只对齐 **Host 何时 mint N**。各 IG 仍各刷各的 VSync；接缝要齐是 Present Barrier / Swap / Framelock，见帧同步总结。

### 7.4 三套集合点不要混名

| 集合点 | 作用 |
| --- | --- |
| **SofGated**（§4.2.2） | Host 只认 **一台 master** 的 SOF 再发下一包 |
| **等齐所有 IG SOF** | 全通道仿真步进 lockstep（本项目初步不做） |
| **Present Barrier** | 渲完 N 再一起 Present（帧同步层；SOF 相位相反） |

### 7.5 与时钟、帧同步的边界

- Timestamp 消费是 ICD 给**异步**建议的延迟补偿，不是 §4.2 全文。两种节拍都可以继续填 `TimeStampValid=true`。
- 统一 Host Frame Number 扇出 **不依赖** §4.2.2：一次 `flush` 给全体填同一个号即可。
- Message Sync 与 Present Barrier **正交**：前者管 N 何时到达入口，后者管已经是 N 之后何时一起翻页。
