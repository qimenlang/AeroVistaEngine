纯靠“服务器下发时间戳做时间同步”，**不能单独解决渲染同步**。它通常只覆盖“时钟对齐”这一层；多通道画面是否同帧、同相、无撕裂，还依赖帧同步、显示相位锁定、延迟补偿和状态一致。

## 多通道同步模块：从 0 到 1 通常要覆盖什么

按层次拆开，成熟方案基本都包含这些能力。**四个分类互相独立，各解决一个不同的问题**：

```text
时钟同步：大家手表一致          （时间基准）
状态同步：大家算同一个世界      （数据内容）
帧同步：  大家同时上屏同一帧    （GPU 换帧时刻）
显示同步：显示器扫描相位一致    （物理扫描时序）
```

### 1. 时钟同步（Time Sync）
- 统一仿真时间，以主机时间为基准，向通道分发；
- 时钟源/协议选型：PTP/IEEE 1588（us）、NTP（ms）、GPS（<us）；
- 估算网络延迟、抖动、时钟漂移并校正（卡尔曼滤波等）；
- **解决的是“大家手表差不多”**，不是“画面同一帧同时出”。

### 2. 状态同步（State Sync）
- 同一仿真步的位姿状态、环境状态、事件等，由主机广播；
- 主从/主备、确定性回放、丢包重传或外推；
- 传输协议：UDP 组播 + 协议：CIGI（Host↔IG）、DIS/HLA（分布式仿真）；
  - CIGI：Common Image Generator Interface（通用图像生成器接口）；
- **解决的是“算的是同一世界状态”**。

> **命令/控制面（Command）**：加载/切库/复位等 Host→IG 指令，可归入状态同步的宽泛范畴（都是 Host 向 IG 传信息），但严格说是**独立控制面**——低频、事件驱动、需精准送达（本项目走 TCP 可靠传输，**无业务回执**），与高频、可丢的状态广播不同。工程上常拆成「UDP 同步面（状态/帧节拍）+ TCP 命令面（控制）」两条链路。

### 3. 帧同步（Frame Sync）
- **本质**：同步「帧号 + Present 时刻」——所有通道渲染第 N 帧，并**同时**把它 swap 出去；
- 帧号对齐：渲染完后，第 N 帧必须全部一起 Present；
- 超时、掉帧时的降级策略（丢帧、重复帧、外推）；
- **解决的是“大家同时把第 N 帧上屏”**（不是“算同一状态”——那是状态同步）。

**帧同步有软有硬，区别在精度，不在本质**：

| 实现 | 手段 | 精度 | 典型场景 |
| --- | --- | --- | --- |
| **软件帧同步** | 统一帧号 + 网络 Barrier + 固定帧率（应用层协调） | 帧号级（跨机仍可能差数 ms） | 研发 / 中低端、非严格拼接 |
| **硬件帧同步** | **Frame Lock / Swap Group / Swap Barrier**（驱动/卡级锁定 Present） | 亚帧 / 亚 ms 级 | 拼接墙、多投影 |

**Frame Lock / Swap Group / Swap Barrier 的关系（同为硬件帧同步，手段与目标不同）：**

```text
Frame Lock（目标）：多 GPU 的 buffer swap 在同一 VSync 沿发生
Swap Group（手段）：把多 GPU 编成一组，组内共享同一 swap 节拍
Swap Barrier（协调）：组内各 GPU 都渲染完第 N 帧后才一起放行 swap
```

| 概念 | 角色 | 类比 |
| --- | --- | --- |
| **Frame Lock** | 能力 / 目标：锁 GPU 换帧时刻到同一 VSync 沿 | 大家约定「整点一起走」 |
| **Swap Group** | 实现机制：把 GPU 编组、共享节拍 | 把大家编成一组、用同一块表 |
| **Swap Barrier** | 协调：等组内都准备好再 swap | 集合点：人等齐了才出发 |

- 三者通常捆绑出现（NVIDIA Quadro Sync 的 `wglJoinSwapGroupNV` + `wglBindSwapBarrierNV` + `wglQueryFrameLockNV`），但概念不同：**Frame Lock 是「要达成什么」，Swap Group 是「怎么达成」，Swap Barrier 是「达成途中的协调器」**；
- 都属**帧同步**（锁 GPU 换帧时刻），**不是**显示同步（Genlock 锁显示器扫描才是显示同步）。

常见模型（软件帧同步）：
- Lockstep：所有客户端 ACK 后主机才推进（延迟高、最稳）
- Predictive + Correction：客户端外推，收到权威状态后修正
- Frame-locked broadcast：主机以固定 Hz 广播，客户端严格按帧号消费

### 4. 显示/交换同步（Display Sync）
- **本质**：同步**显示器的物理扫描时序**——即使帧同步完美（所有 GPU 同时 swap），各显示器 VSync 相位不同仍会造成接缝错位；
- **必须是硬件级**：Genlock 锁显示器扫描（显示同步本体）；Framelock 锁 GPU swap（属帧同步，见 §3，此处作为端到端链路的另一半配套出现），靠专用同步信号/卡实现；
- **解决的是“显示器同一时刻扫同一行”**（不是“GPU 何时换帧”——那是帧同步）。

**与帧同步的关系（核心区分）**：

```text
帧同步   → 管「GPU 何时换帧」（Present 时刻）   —— 软件 Barrier 或硬件 Swap Group 都能做
显示同步 → 管「显示器何时扫屏」（扫描相位）     —— 只有硬件 Genlock 能做到
```

两者都需要硬件级方案时才最精确：Framelock 保证三台 GPU 同时 Present，Genlock 保证三台显示器同时把这一帧扫出去 → 端到端零错位。

- 硬件：NVIDIA Quadro Sync II / AMD FirePro S400；
- 编程接口：WGL_NV_swap_group / GLX_NV_swap_group / DX12 IDXGISwapChain::Present 联动。

    #### **显示同步深入解析**

      一、为什么会撕裂（Screen Tearing）

      显示器工作原理

      显示器不是"一次性把整幅画面亮出来"，而是逐行扫描刷新：
      - 从左上角开始，一行一行、从左到右把像素点亮
      - 到右下角后回到左上（垂直回扫 VBlank）
      - 60Hz 显示器 = 每 16.67ms 完成一次全屏扫描

      同时，GPU 在另一个节奏上工作：
      - 渲染完一帧就把它写入 Front Buffer（显示器正在读取的缓冲区）
      - 或者切换 Back Buffer → Front Buffer（双缓冲，SwapBuffers/Present）

      撕裂的本质

      如果 GPU 在显示器扫描到屏幕中间时切换了 Front Buffer：
      - 屏幕上半部分 = 旧帧的像素
      - 屏幕下半部分 = 新帧的像素
      - 中间出现一条水平错位线 = 撕裂

      ┌─────────────────┐
      │  帧 N（旧）      │  ← 显示器扫描到这里时
      ├─────────────────┤  ← GPU 切换了 buffer
      │  帧 N+1（新）    │
      └─────────────────┘

      二、VSync 的原理

      VSync (Vertical Synchronization) = 让 GPU 的 buffer 切换只发生在垂直回扫期（VBlank）。

      VBlank 是什么

      显示器扫完最后一行后，电子束（或等效信号）需要一段时间"回到"左上角，这段时间不绘制任何像素，称为 VBlank，通常约 0.5~1ms。

      VSync 工作流程

      1. GPU 渲染完一帧，调用 SwapBuffers() / Present()
      2. 驱动不立即切换，而是等待显示器发出 VSync 信号（进入 VBlank）
      3. 在 VBlank 期间安全切换 Front/Back Buffer
      4. 显示器开始新一轮扫描，读到的就是完整新帧

      结果：屏幕永远显示完整帧 → 无撕裂。

      VSync 的代价

      - 延迟增加：GPU 早早渲染完也要等 VBlank，最多多等一整帧
      - 帧率被钉死：只能是 60/30/20 Hz（显示器 60Hz 时），达不到就掉档
      - 卡顿（Judder）：帧率在 60 和 30 之间抖动时感觉明显

      三、多通道场景下的新问题

      单机单屏 VSync 就够了。但三通道飞行模拟器（左/中/右投影或显示器）会遇到：

      问题 A：各显示器的 VSync 相位不同

      即使三台显示器都是 60Hz，它们的扫描起点不同：
      - 显示器 1 的 VBlank 在 t=0, 16.67, 33.33...ms
      - 显示器 2 的 VBlank 在 t=5, 21.67, 38.33...ms
      - 显示器 3 的 VBlank 在 t=11, 27.67...ms

      即使三台 GPU 都开了 VSync，各自的"完整新帧"出现在不同时刻 → 拼接画面出现接缝错位（飞机机翼从左屏"跳"到中屏时会歪一下）。

      问题 B：各 GPU 的 Swap 时刻不同

      三台机器渲染耗时不一样，即使收到"同一帧号"，Present 时刻也不同 → 左屏已显示帧 100，中屏还在显示帧 99。

      这就是 Genlock 和 Framelock 要解决的两件不同的事。

      四、Genlock —— 同步显示器的扫描

      Genlock (Generator Locking)：**让所有显示设备的扫描时序完全一致（同一时刻扫描同一行）**。

      原理

      - 一台设备（或独立信号源）作为 Sync Master，产生 H-Sync / V-Sync 参考信号
      - 其他所有显示器/投影机作为 Sync Slave，用外部信号线接收这个参考
      - Slave 调整自己的扫描起始时刻，与 Master 对齐

      硬件形态

      - 专业投影机/显示器背面有 BNC "Sync In / Sync Out" 接口
      - 或走 Tri-Level Sync（电视广播标准）/ Black Burst
      - 消费级显示器没有 Genlock 输入，物理上做不到

      效果

      三台投影机在 t=0 时都开始扫描第一行，在 t=8ms 时都扫描到屏幕中间 → 拼接墙上任意一行都是同一时刻的图像 → 无接缝错位。

      五、Framelock —— 同步 GPU 的 Swap

      > **归类说明**：Framelock 严格属于**帧同步**（锁 GPU 换帧时刻），此处放在显示同步深入解析里，是因为它是「显示器扫描 + GPU 换帧」组合中 GPU 侧的那一半，与 Genlock 常成对出现、需一起理解。

      Framelock：让多台 GPU 的 Present() / SwapBuffers() 在同一 VSync 边沿发生。多张 GPU 的 SwapBuffers 被硬件强制对齐到同一个 vsync 沿才真正翻转前后缓冲。

      "在同一 VSync 边沿发生"是什么意思

      假设三台 GPU 分别渲染左/中/右画面：
      - 没有 Framelock：GPU-A 在 VSync #100 换帧，GPU-B 在 VSync #101 换帧 → 一屏领先另一屏一帧
      - 有 Framelock：三台 GPU 必须都准备好帧 N 后，同时在 VSync #100 那一刻换帧
      - 如果 GPU-B 慢了一帧还没渲染完 → 三台一起再等一个 VSync（帧率整体下降，但绝不错位）

      原理

      - 一张 Sync 卡（如 NVIDIA Quadro Sync II）插在每台机器上
      - 卡之间用 RJ45 线菊花链连接，形成一个 Sync Group
      - Master Sync 卡产生统一节拍（也可锁到外部 Genlock 信号）
      - 驱动层拦截 Present() 调用，在收到 group-wide barrier 信号后才提交
      - 编程接口：WGL_NV_swap_group / GLX_NV_swap_group / DX12 有对应扩展

      与 Genlock 的关系

      ┌───────────┬──────────────────────┬───────────────┐
      │   概念    │       同步的是       │   硬件位置    │
      ├───────────┼──────────────────────┼───────────────┤
      │ Genlock   │ 显示器扫描时序       │ 显示器/投影机 │
      ├───────────┼──────────────────────┼───────────────┤
      │ Framelock │ GPU buffer swap 时刻 │ GPU/显卡      │
      └───────────┴──────────────────────┴───────────────┘

      理想情况下两者结合：Framelock 保证三台 GPU 同时 Present，Genlock 保证三台显示器同时把这一帧扫描出去 → 端到端零错位。Quadro Sync 卡通常同时支持两者：既做 GPU   间 Framelock，也能接收/输出 Genlock 信号给显示器。

      六、软件同步 vs 硬件同步

      软件同步

      做法：应用层通过网络协调，如"**主机广播帧号 N，所有客户端渲染完 N 后 barrier 等待，再一起 Present**"，**配合每台机器各自的 VSync。**

      优点
      - 零硬件成本（普通显卡、普通显示器）
      - 灵活，可跨平台、跨 GPU 厂商
      - 适合非严格拼接场景（如各屏内容独立的教官台）

      缺点
      - 只能同步到"同一帧号"，无法同步到同一 VSync 边沿
      - 各显示器 VSync 相位不同 → 拼接墙上仍有错位（最多差半帧 ≈ 8ms）
      - 网络抖动直接影响同步质量
      - 各 GPU 渲染耗时不同 → Present 时刻抖动
      - 撕裂/接缝错位对快速运动物体（掠海飞行）非常明显

      适用：低成本训练器、非拼接多屏（如仪表屏 + 视景屏分离）、原型验证。

      硬件同步（Genlock + Framelock）

      做法：Quadro Sync II（或等效）+ 支持 Genlock 的投影机 + 同步信号线。

      优点
      - 物理层保证同一像素时刻显示同一帧
      - 亚微秒级精度，与网络状态无关
      - 拼接墙、球幕、CAVE、LED Volume 的唯一正确解
      - 允许高刷新率下（120Hz、主动立体）稳定同步

      缺点
      - 成本高：每台机一张 Sync 卡（数千~上万元）、专业投影机（十万级起）
      - 需要专用布线（BNC/RJ45 同步线）
      - 绑定 GPU 厂商（NVIDIA Quadro / AMD FirePro 专业线）
      - 部署复杂，需现场调试相位、极性
      - 一台 Slave 挂了整个 Sync Group 可能降级

      适用：全动飞行模拟机（FFS Level D）、军用视景系统、虚拟制片 LED 墙、指挥中心大屏。

      七、飞行模拟器的典型组合

      民航 Level D 全动模拟机 / 军用高等级 IG：
      仿真主机
         ↓ (千兆网, CIGI/HLA, PTP 时钟)
      IG-Left    IG-Center    IG-Right      ← 三台渲染机
         ↓          ↓            ↓
      Quadro Sync ─ Quadro Sync ─ Quadro Sync  ← RJ45 菊花链, Framelock
         ↓          ↓            ↓
      投影-L  ←── 投影-C(Master) ──→ 投影-R    ← BNC 同步线, Genlock

      - 软件层：CIGI 保证帧号/仿真时间一致
      - Framelock：三台 GPU 同一 VSync 边沿 Present
      - Genlock：三台投影机同一时刻扫描同一行像素
      - 端到端可做到 <1ms 通道间错位

    ---
      一句话总结：
      - **撕裂 = GPU 换帧和显示器扫描不同步**
      - **VSync = 单机把换帧对齐到 VBlank**
      - **Genlock = 多显示器扫描时序对齐**
      - **Framelock = 多 GPU 换帧时刻对齐**
      - 软件同步只能对齐"帧号"，硬件同步才能对齐"时刻"，飞行模拟拼接墙必须用硬件同步。

### 5. 视点与投影一致性（View Consistency）
- 每通道有独立的 view frustum（航向角、俯仰、FOV、非对称投影）
- 几何校正、边缘融合、颜色亮度匹配（warp/blend）
- 主眼点（eyepoint）统一，防止视差错位
- **解决的是“接缝处几何/亮度连续”**

### 6.监控与故障恢复
  - 心跳、丢包统计、帧延迟统计
  - 掉线通道自动 rejoin、状态快照重传
  - 教官台可视化每通道同步质量

## “服务器下发时间戳”够不够？

**不够，而且常被误解。**

| 只做时间戳同步能做到 | 还做不到                       |
| -------------------- | ------------------------------ |
| 客户端时钟大致对齐   | 同一仿真帧同一时刻 Present     |
| 降低“时间基准漂移”   | 垂直刷新相位对齐（无相对撕裂） |
| 辅助插值/外推        | GPU Swap 屏障式硬同步          |
|                      | 投影仪/显示链路相位锁          |
|                      | 通道间处理延迟差补偿           |

更准确的模型是：

```text
时间同步 ≠ 状态同步 ≠ 帧同步 ≠ 显示相位同步
      ↓         ↓         ↓           ↓
   时钟对齐   同一世界状态  Swap对齐    VBlank对齐
```

**常见可落地组合：**

1. **软同步（软件为主，= 帧同步的软件实现）**：统一仿真帧号 + 网络 Barrier + 固定帧率  
   - 成本低，适合研发/中低端；只能对齐到帧号，跨机仍可能有数毫秒级错位  
2. **硬同步（产业级，= 帧同步的硬件实现 + 显示同步）**：Genlock/Frame Lock + Swap Group/Barrier + 统一帧号  
   - 飞行模拟、球幕/多投影常用，才是“肉眼无相对抖动”的正经方案  
3. **混合**：PTP/帧号做逻辑同步，GPU/显示做物理相位同步，慢链路做延迟标定  

所以：**时间戳是必要基础之一，但不是渲染同步的充分条件。** 帧同步（软或硬）+ 显示同步（Genlock）缺一不可，单靠时间戳只解决时钟层。

## 业内成熟方案（可对标）

### A. GPU / 显示层硬同步（图像生成器 IG 首选）
- **NVIDIA Quadro Sync / Frame Lock + Swap Group/Swap Barrier**  
  (`WGL_NV_swap_group` / 对应 Vulkan/驱动扩展)  
  多卡/多机同步 Present + 外部 house sync
- **AMD FirePro / Radeon Pro Sync**（同类角色）
- **Genlock / Tri-level / Black Burst**：投影机、广播级显示用外部同步源

### B. 实时引擎集群方案
- **Unreal nDisplay + Cluster Sync**（多机多屏/LED 墙成熟度高）
- **Unity Cluster Display / 多机方案**（成熟度通常弱于 nDisplay，需自研补齐）
- **OSG / OpenSceneGraph 多通道、Slave Camera**（传统视景软件常见，但仍需底层 Swap/Genlock）

### C. 仿真协议与体系
- **CIGI**：Host 与 IG 的标准交互（控制、实体、大气等）
- **DIS / HLA**：分布式仿真互操作与状态分发
- **IEEE 1588 PTP**：亚毫秒级时钟同步（比 NTP 更适合实时）

### D. 投影融合与通道系统
- **Scalable Display / ImmersaView / Barco** 等 warp-blend + 同步链路  
  工程上常是：仿真引擎出多通道 + GPU Sync + 投影融合系统

### E. 航电/飞仿行业常见落地形态
1. Host 推仿真步/帧号（或 CIGI）  
2. 各 IG 算同一帧视景  
3. GPU Swap Barrier + Frame Lock/Genlock  
4. 投影机跟家用同步信号  
5. 出厂做通道延迟与融合标定

## 从 0 到 1 建议的模块切分（实现清单）

若你要自研“多通道同步模块”，建议按可交付包拆：

1. **SyncClock**：PTP/主站时间 + 漂移估计  
2. **FrameDirector**：全局帧号、固定步长、Present 栅栏  
3. **StatePayload**：每帧需对齐的最小状态集（眼点、实体增量等）  
4. **PresentBarrier**：本机多 GPU / 跨机 Barrier（先软后硬）  
5. **DisplayLockAdapter**：对接 Quadro Sync / Genlock（可插拔）  
6. **LatencyCompensator**：通道延迟标定表 + 对齐策略  
7. **ChannelConfig**：视锥、warp/blend、角色、拓扑  
8. **Watchdog & Telemetry**：丢帧、错帧、相位误差、网络 RTT 监控  

**验收指标建议直接量化：**
- 通道间 Present 时间差（µs/ms）  
- 帧号不一致率  
- 接缝相对抖动（视觉/高速摄像）  
- 端到端运动到光子延迟  
- 掉帧与恢复时间  

---

## 结论

- 多通道同步模块 = **时间 + 状态 + 帧呈现 + 显示相位 + 延迟标定 + 管控容错**，不是单一“时间戳服务”。  
- **服务器下发时间戳有用，但只解决时钟层；渲染同步必须再做帧屏障/帧号对齐，工业级还要 Genlock/Frame Lock。**  
- 业内可优先对标：**NVIDIA Quadro Sync + Swap Group**、**PTP**、**CIGI/DIS(HLA)**、**Unreal nDisplay**，投影场景再叠加专业 warp/blend 与家用同步。
