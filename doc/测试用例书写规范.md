# 测试用例书写规范

面向本仓库 Catch2 用例（尤其 `engine/Tests`），总结自 AI+ATDD/TDD 实践与对 `EngineConfigTests` / `RenderingTests` / `HostIGTests` 的规范化改写。

核心原则：**形式 ≠ 层级**；**钉可观察契约，不钉实现细节与 JSON 字面量**；**一 Scenario 一事**。

---

## 1. 先定角色，再选形式

写用例前先回答：失败时，产品/规格语言能否听懂？测的是收货，还是接线/协议，还是局部算法？


| 角色 | 问什么 | 推荐形式 | 推荐标签 |
| ---- | ------ | -------- | -------- |
| **验收** | 该不该按约定收货？ | `SCENARIO` + Given/When/Then | `[acceptance][bdd]…` |
| **集成** | 模块/协议拼起来接得对不对？ | `SCENARIO` 或 `TEST_CASE` | `[integration]…` |
| **单元** | 这段实现算得对不对？ | 默认 `TEST_CASE` | `[unit]…` |

口诀：

- **技术拼装 / API 标尺** → `TEST_CASE`（或不要挂 `[acceptance]`）
- **交付故事 / 对外行为** → `SCENARIO`
- 不要因为写了 `SCENARIO` / `[bdd]` 就自称 ATDD 验收

本仓库已用标签示例：

- `[acceptance][bdd][config|render|sync][hostctrl|e2e|…]`
- `[integration][sync][connect|status|engine|…]`
- `[unit][config][cli]`、`[unit][camera]`

CI 可按标签分层跑：验收冒烟、集成全量、单元快速。

## 2. ATDD / BDD 叙事规范

### 2.1 一 Scenario 一事

- 一个 Scenario 只验收**一个可判定结果**。
- 不要把「失败 → 成功 → 再断连」捆成一条超长故事；拆成独立 Scenario（共享的准备可复制或抽 helper）。
- `AND_WHEN` / `AND_THEN` 仅用于**同一收货故事**的自然续写，不要用来串联多个独立契约。

### 2.2 Given / When / Then

| 步骤 | 写什么 | 避免 |
| ---- | ------ | ---- |
| **Given** | 前置**状态**（已加载配置、已连接、离屏引擎…） | 实现步骤说明书（「调用 init 第 3 步」） |
| **When** | 触发的**用户/系统动作**或可观察事件 | 测试手法当故事（见下） |
| **Then** | **可机器判定**的对外结果 | 「画面好看」、含糊观感 |

Then 优先：成功/失败、位姿误差阈值、像素差%/PSNR、节点数、错误码、是否启 Host、窗口几何是否与配置一致等。

### 2.3 故事语言 vs 测试手法

- **标题与 When**：写行为（「Host 眼点到达后相机跟随」），不写手法（「queue-injected」「mock 了某某」）。
- **注入 / mock / 桩**：可以写在**注释或代码里**，作为稳定测应用逻辑的手段；与真报文 E2E **分开 Scenario**，勿混在同一故事里既要稳又要真。
- 领域词（Host / IG / 通道 offset）可用；实现词（`LookAt`、`WindowTraits`、`FrameCntr`）慎入**验收**标题——更适合集成/单元。

### 2.4 钉规则，不钉快照字面量

配置类用例（约定见 [多通道同步模块设计.md](./design/多通道同步模块设计.md) §3.1）：

- **好**：省略 `-c` 时默认 ≡ `default.json`（无同步；与 `loadEngineChannelConfig` 比对）；有 `hostLocal` → 启 Host，有 `igLocal` → 启 IG；`requireConnectedIg` 缺省恒 `false`（main 须显式 `true`）；运行时地址对齐 `engine.config.*`；未知 JSON 键应加载失败。
- **差**：在测试里写死 `8000/8100/640…` 整表镜像；仍用 `channelId==0` 断言启 Host；配置文件一改，契约语义没变却整批红。

例外：明确的**表征测试 / 黄金图**允许钉参考产物，但改动须显式更新参考，并在标题/标签标明（如 `[golden]`）。

## 3. 分层与配比（本工程约定）


| 量级 | 内容 | 形式 |
| ---- | ---- | ---- |
| 大量、快速 | 数学、工具、状态机、纯 API | `[unit]` + `TEST_CASE` |
| 中量、对接 | HostSync/IgSync 连接、IGCtrl/SOF、帧交换 | `[integration]` |
| 少量、钉契约 | 加载/失败、黄金图、Host 眼点门控与 offset、E2E 多通道 | `[acceptance][bdd]` |
| 发布前补充 | 观感、极端组合 | QA / 探索（自动化盖不住的） |

- 不要把全部单测改成 BDD。
- 不要为同一契约同时保留等价的 `TEST_CASE` 与 `SCENARIO`。
- **AI+ATDD**：人写/人审验收与关键集成的 Then；AI 不得擅自改断言含义刷绿。

## 4. 改写既有用例的整体思路（方法）

对「已有一堆 SCENARIO」做规范化时，按下面顺序扫，而不是先纠结文案润色：

1. **定角色**  
   这条失败时谁该听懂？收货 → acceptance；协议/接线 → integration；API/算法 → unit。

2. **改标签**  
   去掉「一律 `[bdd]`」；补上 `[acceptance]` / `[integration]` / `[unit]`。

3. **拆多故事**  
   标题里出现 then/then/then、或多层 `AND_WHEN` 串生命周期 → 拆 Scenario。

4. **降级错挂的验收**  
   相机 LookAt 标尺、CLI 路径解析等 → `TEST_CASE` + `[unit]`。

5. **去手法词、留行为**  
   标题/When 去掉 queue-injected 等；注入留注释。

6. **松绑字面量**  
   配置比对改为「对文件 / 对 `engine.config`」，少写死端口与路径常量（资源路径、`RESOURCE_DIR` 除外）。

7. **合并重复故事**  
   同一收货（如窗口 traits 与 extent）可并成一个 Then，避免两次 init 讲同一件事。

8. **跑分层过滤确认**  
   例：`vsgEngineTests "[acceptance]"` / `"[integration]"` / `"[unit]"`。

## 5. 自检清单（提交前）

- [ ] 标签是否反映真实层级（acceptance / integration / unit）？
- [ ] 是否一 Scenario 一事？
- [ ] Given 是否状态、Then 是否可机器判定？
- [ ] 标题是否避免测试手法与过度实现词？
- [ ] 配置/协议是否钉规则而非整表字面量？
- [ ] 注入测与 E2E 是否分开？
- [ ] AI 若参与实现：Then 含义是否经人审且未被改松？

---

## 6. 与 AI+ATDD/TDD 的衔接

- **批量 ATDD 第一波**：按小功能一次性写/审本切片验收（及必要集成）；再实现跑绿。
- **追加波**：发现缺口再增 Scenario（规格增量），不是实现写完后随便补测装饰。
- 人守规格与 Then；机器（CI）证明没撒谎；格式/风格门禁不替代行为契约。

更完整的概念与分层说明见 `doc/notes/AI+TDD总结.md`。
